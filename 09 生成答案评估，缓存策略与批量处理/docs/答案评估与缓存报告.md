# 答案评估与缓存报告

> **状态：已完成** — 阶段 0–6 全部通过（2026-07-08）
>
> **本阶段范围**：多维度答案评估器、生成结果缓存、批量并行处理、统一粘合流水线  
> **不包含**：人工标注平台、在线 A/B、分布式缓存（Redis）  
> **验证模式**：默认 `offline`（复用 08 `generation_eval.json` 快照）；可选 `live`（Ollama）

---

## 1. 概述

本阶段在 08 端到端生成能力之上，补齐 RAG 链路的**质量保障与工程优化层**：

- **08**：生成执行 → `answer` + `sources`
- **09（本阶段）**：评估 + 缓存 + 批量调度 → `generation` + `evaluation` + `cache`

### 1.1 端到端数据流

```text
query
  ↓ GenerationCache lookup(key=hash(query, context, model, temperature))
  ├─ HIT  → 复用缓存 generation
  └─ MISS → ModelAdapter.generate()（默认复用 08 快照或 live pipeline）
  ↓ AnswerEvaluator.evaluate()
  ↓ 统一输出 { generation, evaluation, cache, extensions }
```

### 1.2 验证范围说明（必读）

> 与 06「验证范围说明」、08 §1.2 对齐：**本阶段报告中的 ROUGE / key_info_recall 数值，是在样本库检索链路上测得的，不能代表全量 PMC 语料上的最终 RAG 质量。**

| 维度 | 本阶段实际使用 | 说明 |
|------|----------------|------|
| 检索语料 | 06 样本库 **`mode="sample"`**（**1,267** chunks） | 见 `06 .../schedule.md` §「验证范围说明」；非 610 万全量 |
| 检索输入 | 06 `pipeline_eval.json` 离线 reranked（每条约 5 候选） | 08 `OfflineRetrievalAdapter` 读取；`generation_eval.json` 标注 `offline_sample_pipeline_eval` |
| 生成答案 | 08 `generation_eval.json` 四条快照（offline 默认） | 09 `SnapshotModelAdapter` 复用，不重新跑 Ollama |
| 评估基准 | `data/ground_truth.json` 四条人工 reference + key_phrases | 临床指南型参考文本，**非**从样本库自动抽取 |
| 缓存 / 批量 | 进程内 LRU+TTL；`BatchRunner` 四条并行 | 与语料规模无关，本阶段已验证链路 |

**数据链路**：

```text
06 pipeline_eval.json (sample, 1,267 chunks)
  → 08 run_generation_eval.py (OfflineRetrievalAdapter + Ollama)
  → 08 generation_eval.json (快照)
  → 09 run_eval_cache_batch.py --mode offline (SnapshotModelAdapter)
  → AnswerEvaluator vs ground_truth.json
```

**对指标解读的影响**：

- ROUGE / key_info_recall 偏低，**与样本库覆盖不足直接相关**：样本中常缺 MI 标准治疗、metformin 心血管获益等专题文献，生成答案会如实表达「context 未提供」。
- 例如 Q1（`What is the treatment for MI?`）在 `pipeline_eval.json` 中**无精确匹配 query**（仅有 `MI treatment guideline`），08 评测走 **fallback reranked**，命中 homocysteine / CABG 应激等弱相关 chunk（relevance_score≈0.28），故 `key_info_recall=0` 可预期。
- 本阶段验证目标是 **09 评估/缓存/批量链路正确性**，不是在全量库上追求高分；全量复评见 §5.7、`schedule.md`「全量验证」。

| 项 | 本阶段 notebook / CLI 验证 | 说明 |
|----|---------------------------|------|
| 生成输入 | 08 `generation_eval.json` 四条快照（offline） | 不依赖实时 Ollama，便于复现 |
| 评估基准 | `data/ground_truth.json` 四条 reference + key_phrases | 与 08 `DEFAULT_QUERIES` 对齐 |
| 缓存 | 进程内 LRU + TTL + 低温门控 | 进程退出即失效（MVP 边界） |
| 批量 | `BatchRunner` 多 query 并行 | 单 query 内部仍串行 |
| live 模式 | `--mode live` 仍用 06 样本 `pipeline_eval.json` | 仅重跑生成，检索未切 `from_mode("full")` |

### 5.1 持久化缓存后端

`config.cache_backend`（默认 `memory`；后续可考虑 `sqlite` / `redis`）

**当前实现**

- `GenerationCache` 以进程内 `OrderedDict`（`_index`）承载 LRU/TTL。
- `make_key()` 对 `query + context_text + model + temperature_bucket`（保留 2 位小数）做 `sha256`。
- `set()` 受 `max_temperature=0.3` 门控，TTL 取 `config.ttl_seconds=86400`（24h）。
- `BaseCacheBackend` / `MemoryCacheBackend` 已定义，但 **`config.cache_backend` 未被读取**；实际读写均走 `_index`（仅 `delete()` 会调用 backend）。

**实测验证**

- `eval_cache_batch_report.json`（offline）：首轮 `hit_rate=0.0`（4 miss），第二轮 `hit_rate=1.0`（4 hit）。
- 进程重启后缓存清空；`force_refresh=True` 可绕过命中（`test_pipeline_with_eval.py` 已覆盖）。

**扩展落点**

- 在 `GenerationCache.__init__` 按 `cache_backend` 选择后端，将 `get/set` 从 `_index` 下沉到 backend。
- 持久化优先考虑 `sqlite`（单机）或 `redis`（多实例共享）。

**设计权衡**（Q4-1、Q4-4）

- 缓存命中判断「输入场景是否相同」（query + context + model + temperature），与 ROUGE 等输出质量指标无关——两者并列，一个管性能、一个管质量。
- MVP 进程内 LRU+TTL 已验证重复调用收益；进程退出即失效在开发期可接受。
- 上线或多实例、需跨重启复用时再升级持久化；TTL 开发期 24h，稳定后可配 24h~7d，医学内容宜保守并保留 `force_refresh`。

### 5.2 引用联动幻觉降权

`evidence_linked_hallucination_scoring`；当前按 `patterns.py` 规则计分，后续加「有引用降权」

**当前实现**

- `detect_hallucination_signals()` 匹配 4 类正则（`studies show`、`has been proven`、`100%`、绝对安全/有效表述），权重写死在 `HALLUCINATION_SIGNAL_PATTERNS`。
- `evaluate()` 已将 `generation.sources` 传入 `link_signals_with_sources()`，但该函数**当前透传**（`sources` 未参与计算）。
- `config.hallucination_weight_profile` 已声明，**未被读取**。模块 docstring 明确：幻觉分为风险信号，非真伪裁定。

**实测验证**

- offline 四条快照：`hallucination_risk_avg=0.0`，`hallucination_signals` 均为 `[]`——快照未触发规则，**尚无法从产出验证降权逻辑**。
- 单测 `test_detect_hallucination_signals` 对含 `100%` 样例可检出信号。

**扩展落点**

- 在 `link_signals_with_sources()` 实现「有 `sources` 时按 `hallucination_weight_profile` 降权」。
- 权重配置从 `patterns.py` 迁移到 `config` 或 profile 文件。

**设计权衡**（Q4-3）

- 绝对化表述规则定位为**风险筛查**（`risk signal`），不是真伪终审。
- 若原论文本身表述绝对、模型如实复述，规则仍可能标高风险——「宁可保守提醒」的可预期误报。
- 降误报需联合 08 `sources`：有明确引用时降低严重等级（绝对词+无引用权重高，有来源权重低），而非直接判错。

### 5.3 语义级关键信息匹配

`semantic_key_info_match`；当前 `key_phrases` 子串匹配，后续可考虑 embedding 语义匹配

**当前实现**

- `key_info_recall()` 对 `ground_truth.json` 的 `key_phrases` 做规范化（小写、压缩空白）后做**子串包含**判断，`recall = matched / len(gt_phrases)`。
- `extract_key_info()`（正则+关键词）已实现但 **未参与 recall 计算**。
- ROUGE 由 `rouge_score.RougeScorer` 独立输出，与 recall 无耦合。

**实测验证**

- offline 首轮：`rouge1_avg=0.0768`，`key_info_recall_avg=0.2321`（见 §4.2、§4.3）。
- 逐条 recall：MI=0.0（7 短语全漏）、metformin=0.0、malaria=0.5、warfarin=0.4286。
- 同义改写或词形变化（如 `statins` vs `statin`）当前**不会**计为命中。

**扩展落点**

- 新增 `semantic_recall` 字段（embedding 相似度阈值），与现有子串 recall 并列输出，不替换现有指标。

**设计权衡**（Q4-2）

- 任务书 `recall = overlap / gt_matches` 的工程落地是「`key_phrases` 短语重叠」，能判断关键点是否被覆盖，**不能**证明模型从正确证据链推导。
- 09 评估是自动近似，非医学事实终审；更稳妥应联合 08 `sources`、key_info_recall、幻觉风险及人工 spot check。
- ROUGE 对结构化答案可能偏低，故与 recall 并列展示；语义匹配作为补充而非替代。

### 5.4 自适应 TTL 策略

`config.ttl_policy`（当前 `"fixed"`）；后续按 query 类型动态 TTL

**当前实现**

- `GenerationCache.set()` 统一使用 `self.ttl_seconds`（默认 86400）；**`config.ttl_policy` 未被读取**。
- 强制刷新由 `run_with_cache_and_eval(force_refresh=True)` 实现，跳过 `get` 直接重算。

**实测验证**

- 单测 `test_ttl_expiration_returns_none` 验证过期后 `get` 返回 `None`。
- CLI/notebook 两轮同参复跑第二轮全命中；**未覆盖**按 query 类型差异化 TTL。

**扩展落点**

- 在 `set()` 入口根据 `ttl_policy` 与 query 元数据（如 `ground_truth.json` 标签）选择 TTL；保留 `force_refresh`。

**设计权衡**（Q4-4）

- 固定 TTL 满足 MVP「可控时效 + 可复现实验」。
- 不同 query 时效敏感度不同（治疗指南 vs 文献检索），动态策略可在复用收益与知识过时风险间折中。
- 医学内容建议偏保守，并始终保留 `force_refresh=True`，避免错误结论被长期复用。

### 5.5 自适应并发调参

`auto_tune_max_workers`；当前静态 `max_workers`，后续按失败率/延迟动态调整

**当前实现**

- `BatchRunner.__init__` 取 `min(config.max_workers, min(4, os.cpu_count() or 1))`，默认上限 4。
- `run_batch()` 用 `ThreadPoolExecutor` 并行多 query；`summarize()` 输出 `avg_latency_seconds`、`error_rate`，**但不回写** `max_workers`。
- 并行边界：多 query 并行，单 query 内部 08 阶段仍串行。

**实测验证**

- `eval_cache_batch_report.json`：`max_workers=2`，`error_rate=0.0`，`avg_latency_seconds=0.0041`（offline 快照，无真实 LLM 等待）。
- live 模式下 Q1 `generation_metrics.total_time_seconds≈33.4`，瓶颈在推理而非 CPU。

**扩展落点**

- 在 CLI 或 `BatchRunner` 外层增加「上一轮 `summarize()` → 调整下一轮 `max_workers`」闭环（如 `error_rate > 0` 或 P95 延迟超阈值则降并发）。

**设计权衡**（Q4-5）

- 并行发生在**多 query 批处理层**，单 query 内 08 四阶段仍串行——不是「每个 stage 并行再跑一次 LLM」。
- `max_workers = min(4, cpu_count)` 是保守起点；真实瓶颈常在 Ollama 推理与 I/O，非纯 CPU。
- Ollama 排队/超时时宜降至 2，稳定可试 3~4；需结合实测延迟与失败率动态调。
