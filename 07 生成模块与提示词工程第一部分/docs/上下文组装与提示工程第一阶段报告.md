## 1. 概述

本阶段在 06 多路检索与重排序流水线之后，实现 **上下文组装（Context Assembler）** 与 **医学提示工程模板（Prompt Stages）**，为后续 LangChain RAG 的答案生成链路提供标准化输入。

### 1.1 在 RAG 链路中的位置

```
用户 query
    ↓ 05 MedicalQueryEnhancer
    ↓ 06 RetrievalPipeline（向量 + BM25 → 融合 → rerank）
    ↓ 【本阶段】ContextAssembler（去重 / 多样化 / 控长）
    ↓ 【本阶段】PromptStage × 4（渲染 system + user prompt）
    ↓ （后续）LLM 推理 → 最终回答
```

### 1.2 输入与输出

| 项目 | 说明 |
|------|------|
| **上游输入** | 06 `result["reranked"]`（首选）或 `result["retrieval"]["fused"]`（退化） |
| **输入契约** | 见 [`输入候选格式约定.md`](../输入候选格式约定.md) |
| **组装输出** | `AssembledContext`：`context_text` + `metadata` + `selected_chunks` |
| **Prompt 输出** | 四阶段 `dict` payload：`stage` / `system_prompt` / `user_prompt` / `temperature` / `max_tokens` |
| **本阶段不做** | LLM API 调用、多阶段 LLM 输出串联、答案后处理 |

## 2. 模块设计

### 2.1 数据结构与 06 对接（`models.py`）

| 类型 | 职责 |
|------|------|
| `DocumentChunk` | 统一文档块：`text` / `metadata` / `relevance_score` / `source` / `chunk_id` |
| `ContextMetadata` | 组装统计：检索数、去重后数、入选数、估算 token、来源分布 |
| `AssembledContext` | 最终产物 + `to_dict()` |
| `document_chunk_from_candidate()` | 单条 06 候选 → `DocumentChunk` |
| `coerce_to_document_chunks()` | 批量转换，跳过无效 `text` |

**相关性分数映射**：优先 `rerank_score` → `fusion_score` → `score` → `vector_score`。

### 2.2 上下文组装器（`context_assembler.py`）

`ContextAssembler.assemble()` 流水线：

```
06 候选列表
    → coerce_to_document_chunks
    → dedup_by_jaccard（按 relevance 降序，保留高分）
    → _order_with_diversity（同源 doc_id 超配额降权）
    → _build_context（按 token 预算拼接，必要时截断）
    → AssembledContext
```

| 策略 | 默认参数 | 说明 |
|------|----------|------|
| Jaccard 去重 | `dedup_threshold=0.85` | 与 06 BM25 分词风格一致的轻量 token 集 |
| 多样化 | `max_per_source=2`，`source_penalty=0.15` | 按 `doc_id` 计同源，超额条目降权 |
| token 控长 | `max_context_tokens`（默认 2048） | 多块以 `\n\n` 拼接 |
| 句号截断 | 末 10% 文本内找 `.` `!` `?` | 无句号则硬截断到字符边界 |

### 2.3 提示工程模板（`prompts.py`）

四阶段为 **医学 RAG 多步 Prompt 剧本**（流水线串行设计，非用户四选一模式）：

| key | 中文名 | temperature | max_tokens | 角色 |
|-----|--------|-------------|------------|------|
| `evidence_evaluator` | 证据评估器 | 0.1 | 900 | 审证据强弱与矛盾，不给临床建议 |
| `answer_generator` | 答案生成器 | 0.2 | 1200 | 基于 context 起草答案并引用 |
| `critical_reviewer` | 批判性审查器 | 0.0 | 800 | 挑过度断言、补安全提示 |
| `final_assembler` | 最终组装器 | 0.1 | 1000 | 合并修订，输出结构化终稿 |

**统一占位符**：`{question}` `{context}` `{constraints}` `{output_format}`  
**渲染入口**：`render_prompt_stage(stage_key, ...)` → 可直接对接 LLM 推理接口。

> **当前简化**：四阶段共用同一 `context`；尚未把上一阶段 LLM 输出注入下一阶段（留给 LangChain 全链路实现）。

payload = render_prompt_stage(
    "answer_generator",
    question="metformin cardiovascular effects",
    context=assembled.context_text,
    constraints="Use only evidence in context.",
    output_format="JSON with answer and evidence_points",
)
# payload["user_prompt"] → 后续 LLM 调用

## 6. 风险与后续工作

| 风险 | 应对 |
|------|------|
| tokenizer 与目标 LLM 不一致 | 上线前按实际 LLM 统一 tokenizer；当前 notebook 默认启发式 `len//4` |
| 去重过强 | 调低阈值或按场景关闭 |
| 截断无句号 | 末 10% 无标点则硬截断；可后续改为段落边界 |
| 四阶段未串联 LLM 输出 | LangChain 阶段按 ①→②→③→④ 注入上一步结果 |

**下一阶段建议**：

1. LangChain 封装：`RetrievalPipeline` → `ContextAssembler` → 四阶段 LLM Chain；
2. 生产环境切换 `from_mode("full")` 后复测组装与 Prompt 长度；
3. 按目标模型（Ollama 等）校准 `max_context_tokens` 与 `max_tokens`。
