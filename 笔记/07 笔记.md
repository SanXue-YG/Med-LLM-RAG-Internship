## Q2：三种输入分别是什么意思？什么时候用？

约定文档 §1 列了三种拿候选的方式，本质都是「**一组 dict，每个 dict 是一块文献片段**」，区别在**数据从哪来、排到哪一步**。

### 对照表

| 输入类型 | 代码 / 路径 | 含义 | 典型场景 |
|---------|------------|------|---------|
| **首选：`reranked`** | `result["reranked"]` | 06 流水线**跑完全程**（增强→双路召回→融合→**重排**）后的 Top-K | **正常联调、notebook 演示、最终 RAG** |
| **退化：`fused`** | `result["retrieval"]["fused"]` | 只做到**融合**，**没做** bge-reranker + 年份/期刊重排 | 调试融合策略、或 `skip_rerank=True` 时 |
| **离线：JSON 样例** | `06/.../pipeline_eval.json` → `queries[i]["reranked"]` | 把以前跑好的结果**存盘**，不连库也能测 07 | 单测、没 GPU/没全量库时、CI |

### 用流水线类比

```text
用户问题
   → 05 洗菜（query 增强）
   → 06 两路买菜（向量 + BM25）
   → 06 并菜（融合 RRF）
   → 06 摆盘（重排 rerank）     ← reranked：最终上桌的菜
   │
   │  若跳过摆盘（skip_rerank）
   ▼
   fused：并菜后的半成品，顺序未必最优

07 厨房：从「摆好盘的菜」或「并菜半成品」里，挑份量、去重复、装在一个盘里（context_text）
```

### 为什么 `reranked` 是首选？

- 每条候选带 **`final_score`**（相关性 + 时效 + 期刊等多准则加权），07 按分数**优先选高相关、再多样化**时更靠谱。
- `fused` 只有 **`fusion_score`**（两路排名 RRF 合并），**没有** cross-encoder 精排，相关顺序可能不如 `reranked`。
- 离线 JSON 与在线 `reranked` **字段结构相同**，方便「先离线开发 07，再联机 06」。

### 三种输入在代码里怎么选？

```python
# 生产 / 演示：首选
candidates = result["reranked"]

# 06 开了 skip_rerank，或你只关心融合效果
candidates = result["retrieval"]["fused"]

# 离线：读 06 已导出的评测 JSON
import json
data = json.loads(Path("06 .../pipeline_eval.json").read_text())
candidates = data["queries"][0]["reranked"]
```

## Q3：§2「单个候选的字段」——每张「卡片」上写了什么？

06 每返回一条候选，就是一个 **Python `dict`**（也可序列化成 JSON）。§2 是在说明：**07 从这张卡片里读哪些字、哪些可以当备胎**。

### 三类字段

| 类别 | 字段 | 为什么重要 |
|------|------|-----------|
| **必需（缺了不好干活）** | `chunk_id`、`text`、`doc_id` | 唯一标识、正文内容、判断是否同一篇文献 |
| **排序用（有则用，无则回退）** | `final_score`、`fusion_score`、`relevance_score`、`score` | 决定谁先进入上下文 |
| **解释 / 展示用（全进 metadata）** | `source_title`、`pub_year`、`journal`、`rerank_explain`… | 给 LLM 或用户引用、调试、多样化 |

### 常问字段逐个说

| 字段 | 通俗含义 |
|------|---------|
| `chunk_id` | 这块文字在库里的身份证号，如 `PMC524376_chunk0`（第 0 块） |
| `text` | 真正要拼进 prompt 的内容，一般是 **标题 + 摘要** |
| `doc_id` | 属于哪篇 PMC 文献；同一 `doc_id` 可能有多块（`chunk0`、`chunk1`…） |
| `source_title` | 论文标题，给人看、也给「多样化」用（别全选同一篇） |
| `source` | 从哪条路召回的：`vector` / `keyword` / `fused`（通道名，不是期刊名） |
| `final_score` | **重排后**综合分，越大越该排前面 |
| `fusion_score` | **仅融合**时的分，没 rerank 时用这个当相关性 |
| `vector_score` / `bm25_score` | 单路原始分，便于分析「语义路还是关键词路更准」 |
| `pub_year` / `journal` | 06 从 slim 元数据回查的，07 可留给 prompt 写「据 2015 年 ×× 期刊…」 |
| `token_count` | 06 估的这块多长，07 控总长时可参考 |
| `rerank_explain` | 重排为什么给这个分（调试用） |

**要点**：07 **不强制**候选带齐上表所有可选字段；有就 enrich metadata，没有也能用回退规则跑。

## Q4：§3「→ DocumentChunk 映射」——为什么要转一层？

任务书要求 07 内部用统一的数据类 `DocumentChunk`（5 个字段），而 06 吐出来的是**字段很多的大 dict**。§3 约定：**怎么从大 dict 填进小数据类**。

### 为什么不直接用 06 的 dict？

1. **接口稳定**：以后 06 多加字段，只要映射层吸收，组装器逻辑不用改。
2. **任务书字段就 5 个**：`text / metadata / relevance_score / source / chunk_id`——清晰分工。
3. **`metadata` 是「杂物抽屉」**：年份、期刊、各种 score 都收进去，不丢信息。

### 映射规则（记忆版）

| `DocumentChunk` 字段 | 从哪来 |
|---------------------|--------|
| `chunk_id` | 候选的 `chunk_id`；没有就用 `doc_id`；再没有就临时编号 |
| `text` | 候选的 `text` |
| `relevance_score` | **瀑布回退**：`final_score` → `fusion_score` → `relevance_score` → `score` → `0.0` |
| `source` | **优先文献名**：`source_title` → `doc_id` → 通道名 `source` |
| `metadata` | **剩下全部**塞进 dict |

### 两个容易混的概念

| 名字 | 含义 |
|------|------|
| 06 的 `source` | 召回**通道**（vector/keyword/fused） |
| 07 `DocumentChunk.source` | 展示/多样化用的**文献来源名**（通常是 `source_title`） |

所以 07 的 `source` **不是**简单复制 06 的 `source` 字段——同名不同义，映射表里写清楚了。

### `relevance_score` 瀑布为什么这样设计？

- 吃 **`reranked`** 时，用 `final_score`（最终排序依据）。
- 吃 **`fused`** 时，没有 `final_score`，退到 `fusion_score`。
- 吃更原始的 vector hit 时，可能只有 `score`。
- 都没有就给 `0.0`，避免组装器崩溃。

## Q5：§4「宽松兼容约定」——工程上的容错

不是为了偷懒，是为了 **单测、离线 JSON、半成品 dict** 都能跑。

| 规则 | 含义 |
|------|------|
| 输入可以是 `list[dict]` 或 `list[DocumentChunk]`，甚至混着来 | notebook 里可能已转了一部分；测试里可能只造最小 dict |
| 可选字段缺失不报错 | 按 §3 回退；缺 `pub_year` 照样组装 |
| `text` 为空或不是字符串 → **跳过** | 避免拼进空段落；在 metadata 里统计跳过了几条 |

**类比**：组装器像收简历——必填项（有正文、有 ID）才进下一轮；选填项（期刊、年份）有则加分，没有不拦人。

## Q6：§5「输出契约」——组装器交什么货？

这是 **阶段 2 要实现** 的返回形状，阶段 0 先写清楚，后面写代码和测例都对着这份契约。

```python
{
    "context_text": "...",       # 给 LLM 看的一大段参考资料（已控长、尽量在句号处截断）
    "metadata": { ... },         # 组装过程的统计账本
    "selected_chunks": [ ... ],  # 最终选中的 DocumentChunk 列表（可溯源、可 debug）
}
```

### `metadata` 里各项含义

| 键 | 含义 |
|----|------|
| `total_chunks_retrieved` | 06 一共塞进来多少条候选 |
| `unique_chunks_after_dedup` | Jaccard 去重后剩多少（去掉内容太像的重复块） |
| `chunks_selected` | 去重 + 排序 + 多样化 + 控长后，真正写进 `context_text` 的条数 |
| `estimated_tokens` | 最终上下文大概占多少 token（别超过模型窗口） |
| `chunk_sources` | 来自哪些文献/来源的分布（例如 3 篇不同 PMC、别全是一篇） |

### 和任务书 return 的对应

任务书 `ContextAssembler` 的 return 与 §5 **一致**——`context_text` + `metadata` + `selected_chunks`。本周写组装器时以 §5 为验收标准。

### 和 Prompt 模板的关系

- **`context_text`** → 填进 prompt 的 `{context}` 占位符。
- **`selected_chunks`** → 需要引用「第几条证据」时，可对照 chunk_id / source_title。
- **本周 Prompt 模板**还不消费 LLM 输出，只定义四阶段 `system_prompt` + `user_prompt_template`；真正串联在后续 LangChain RAG。

## Q9：我看 notebook 后的理解对不对？「先本地查数据 → 再交给 LLM 分析 → LLM 在回答里说明数据来源」

### 一句话结论

**大方向是对的。** 完整 RAG 在线链路确实是：

1. **本地**根据用户问题从语料库检索相关文献片段（06，不经 LLM）；
2. **本地**把检索结果整理成受控上下文（07 `ContextAssembler`）；
3. 把 **问题 + 上下文 + 约束 + 输出格式** 填进 Prompt，**交给 LLM** 生成答案（本周 notebook 只做到「渲染 Prompt」，C4 **尚未真正调用 LLM**）；
4. LLM 被 Prompt **要求**基于上下文作答并**引用证据**；来源信息来自 `context` 里的文献标题/摘要文本（以及后续可对接的 `selected_chunks` 元数据）。

需要补上的细节见下文。

### 对照你的三句话

| 你的理解 | 是否属实 | 补充说明 |
|---------|:--------:|---------|
| 先本地根据问题查询数据集 | ✅ **是** | 由 **05+06** 完成：query 增强 → 向量+BM25 检索 → 融合 → 重排；查的是 **Chroma 向量库 + chunks 语料**，不是 LLM 去「上网查」 |
| 再把处理好的数据、问题、约束、输出格式一起交给 LLM | ✅ **是** | **07** 产出 `context_text`；`prompts.py` 用 `{question}` `{context}` `{constraints}` `{output_format}` 拼成 payload |
| LLM 根据处理好的数据在回答里告诉用户采用了哪些来源 | ⚠️ **设计意图是，但取决于 Prompt 与上下文格式** | `answer_generator` 明确要求 *cite supporting evidence points*；当前 `context_text` 是**标题+摘要正文拼接**，未自动加 `[1] PMC520826` 这类编号，LLM 通常只能引用上下文里**可见的标题/句子** |

### 完整流程（notebook 所在位置标 ★）

```text
用户问题 question
    │
    ▼
【05 查询增强】MedicalQueryEnhancer（同义词、实体、vector/keyword query）
    │
    ▼
【06 检索 · 本地、不用 LLM】
    向量路(Chroma) + 关键词路(BM25) → 融合(RRF) → 重排(reranker)
    │
    ▼
候选列表 reranked（每条含 text、doc_id、source_title、score 等）
    │
    ▼
★【07 ContextAssembler · 本地、不用 LLM】
    去重(Jaccard) → 多样化 → 控长截断 → context_text + selected_chunks
    │
    ▼
★【07 Prompt 渲染 · 本地、不用 LLM】（generation-prompting.ipynb C4）
    四阶段模板填占位符 → system_prompt + user_prompt（payload）
    │
    ▼
【后续 LangChain / Ollama · 才调用 LLM】（本周未实现）
    evidence_evaluator → answer_generator → critical_reviewer → final_assembler
    │
    ▼
最终面向用户的答案（应含证据引用与不确定性说明）
```

**记忆**：检索和组装都在 LLM **之外**完成；LLM 只消费已经选好的 `context`，不负责查库。

### 和当前 notebook 的关系（容易误解的一点）

`generation-prompting.ipynb` **C0** 读的是 06 已导出的 **`pipeline_eval.json`**（离线样例），相当于跳过了「当场再跑一遍 06 检索」：

| 模式 | C0 数据来源 | 含义 |
|------|------------|------|
| **notebook 演示（当前）** | `06/.../pipeline_eval.json` → `queries[i]["reranked"]` | 结构与在线 `RetrievalPipeline.run()` 输出一致，便于复现 |
| **生产 / 全链路联调** | `RetrievalPipeline.from_mode("full").run(question)["reranked"]` | 真的会查 Chroma 全量库 + BM25 全量语料 |

所以：**「先本地查数据」在概念上正确**；本 notebook 为演示方便，把「查数据」替换成了「读取上次查好的 JSON」，**07 的组装与 Prompt 逻辑不变**。

### 交给 LLM 的到底是什么？

C4 渲染后，每个阶段的 payload 大致为：

| 字段 | 来源 | 作用 |
|------|------|------|
| `question` | 用户原问题 | 告诉模型要回答什么 |
| `user_prompt` 里的 `Retrieved Context` | `assembled.context_text` | **唯一允许当作证据的正文**（任务书要求 grounded） |
| `constraints` | notebook 里手写字符串 | 如「仅用上下文、勿编造引用、弱证据要说明不确定性」 |
| `output_format` | notebook 里手写字符串 | 如 JSON 含 `answer` / `evidence_points` / `uncertainty` |
| `system_prompt` | `PROMPT_STAGES` 各阶段定义 | 角色与行为（评估器 / 生成器 / 审查器 / 组装器） |
| `temperature` / `max_tokens` | 各 `PromptStage` 配置 | 控制生成随机性与长度 |

**四阶段是未来的多次 LLM 调用剧本**，不是一次把所有内容扔进去就结束；本周只生成这些字符串，不调 API。

### 「数据来源」在系统里怎么体现？

分三层，不要混为一谈：

| 层级 | 存什么 | 谁用 |
|------|--------|------|
| **检索层（06）** | `doc_id`、`source_title`、`chunk_id`、`pub_year`、`journal` 等 | 排序、重排、可追溯 |
| **组装层（07）** | `context_text`（正文）+ `selected_chunks`（含完整 metadata） | `context` 进 Prompt；`selected_chunks` 给程序侧溯源 |
| **生成层（未来 LLM）** | 答案里的 `evidence_points`、引用表述 | 由 Prompt 要求模型根据 `context` 写出来 |

当前 `context_text` 的拼法是：多块 `chunk.text` 用 `\n\n` 连接。PMC 块的 `text` 通常**以论文标题开头**，例如样例里的 `Daily rhythms in plasma levels of homocysteine`，因此 LLM **可以**在回答里写「据 Daily rhythms in plasma levels of homocysteine 一文…」。但 **`chunk_id`（如 PMC520826）默认不在 `context_text` 里**，只在 `selected_chunks[].metadata` 中；若希望答案必须带 PMC ID，需要在组装时给每块加前缀（如 `[Evidence-1 | PMC520826]`），或后处理把 `selected_chunks` 映射进最终展示——这是后续可增强项，不是本周已实现行为。

### 和你问题的直接回答

> 现有流程是不是：先本地查 → 再交给 LLM 分析 → LLM 根据处理好的数据说明采用了哪些来源？

**是的，这就是本工程 RAG「检索增强生成」的主线。** 更准确的说法是：

1. **查**：05+06 在本地语料库检索（LLM 不参与）；
2. **装**：07 把候选变成 `context_text`（LLM 不参与）；
3. **问**：把 question + context + 约束 + 格式填入 Prompt，**由 LLM 生成**（notebook 仅演示到第 2.5 步）；
4. **引**：来源靠 Prompt 约束 + 上下文里的标题/摘要；**不是** LLM 自己去数据库再查一遍，也**不是**系统自动把 `chunk_id` 写进用户可见答案（除非 Prompt/后处理要求）。

### 自测：用 notebook 输出核对

打开 `outputs/samples/assembled_context_examples.json` 与 `prompt_examples.json`：

- `assembled.context_text` → 即将来填进 `{context}` 的正文；
- `selected_chunk_brief` → 程序侧知道的「用了哪几块、对应哪个 doc_id」；
- `prompt_examples.stages.answer_generator.user_prompt` → 可见四段占位符都已填入，且 Task 第 2 条要求 *cite supporting evidence points*。

## Q10：C4 的「四阶段 stages」是什么？是 LLM 可选不同模式吗？

### 一句话

**不是**聊天软件里那种「用户选一个模式」；而是 **医学 RAG 的多步 Prompt 流水线**——把回答过程拆成 4 个不同「角色」的 LLM 步骤，按顺序协作，降低胡编和安全风险。

### 和「可选模式」的区别

| | 本项目的四阶段 | 常见的「LLM 模式」 |
|--|---------------|-------------------|
| 谁选 | **系统/流水线**按剧本自动串行 | 用户或 UI 切换（如创意/精确） |
| 关系 | ①→②→③→④ **协作**，前步输出可供后步参考 | 通常 **互斥**，选一种就只跑一种 |
| 本周状态 | C4 只**渲染**四份 prompt，**未调用** LLM | — |
| 用户看到什么 | 最终应是 **④ 终稿**（未来实现后） | 当前选中模式的单次回复 |

### 四阶段分别做什么？

| key | 中文名 | LLM 扮演 | 核心任务 | temperature（越低越稳） |
|-----|--------|---------|---------|------------------------|
| `evidence_evaluator` | **证据评估器** | 文献审稿员 | 从 context 提炼证据、标 strong/moderate/weak、找矛盾与缺口；**不给最终临床建议** | 0.1 |
| `answer_generator` | **答案生成器** | 谨慎医学助手 | 仅基于 context **起草答案**，要求引用证据、说明不确定性 | 0.2 |
| `critical_reviewer` | **批判性审查器** | 安全审查员 | 挑过度断言、幻觉风险、补禁忌/适用范围，给出修改清单 | **0.0**（最保守） |
| `final_assembler` | **最终组装器** | 终稿编辑 | 合并初稿与审查意见，输出结构化、带来源说明与安全提示的**用户可见终稿** | 0.1 |

### 用生活场景类比

像医院写一份**对外科普材料**，不是一个人一口气写完：

1. **证据评估器**：先把参考文献整理成「证据表」——哪些可靠、哪些有冲突；
2. **答案生成器**：根据证据表写**初稿**；
3. **批判性审查器**：医务处/法务看初稿——哪里说太满、哪里缺「请咨询医生」；
4. **最终组装器**：按审查意见改成**定稿**再发布。

四步可以是**同一只 LLM**（换不同 system prompt），也可以是不同模型；关键是 **Prompt 角色与任务不同**。

### 流水线示意（未来 LangChain 目标）

```text
同一 question + 同一 assembled.context_text
        │
        ▼
① evidence_evaluator  →  证据质量报告（中间产物）
        │
        ▼
② answer_generator    →  答案初稿（中间产物）
        │
        ▼
③ critical_reviewer   →  审查意见 / 修改建议（中间产物）
        │
        ▼
④ final_assembler     →  ★ 给用户看的最终回答 ★
```

> **当前模板简化点**：本周 `prompts.py` 里四步的 `user_prompt` **都填了同一份 context**，尚未把①②③的 LLM 输出再喂给下一步；那是后续 LangChain 粘合层要补的。C4 的作用是证明「四份剧本都能正确渲染」。

### C4 里为什么一次打印四个？

因为 `render_prompt_stage` 对 `PROMPT_STAGES` **四个 key 都跑了一遍**，方便你：

- 检查占位符是否齐全；
- 对比各阶段 `system_prompt` / `temperature` 差异；
- 确认 `prompt_examples.json` 里 `stages` 下有四套完整 payload。

**不是**让你每次提问时手动选其中一个。

### 和 `prompt_examples.json` 的对应

```json
{
  "stages": {
    "evidence_evaluator": { "stage": "证据评估器", "user_prompt": "...", ... },
    "answer_generator":   { "stage": "答案生成器", ... },
    "critical_reviewer":  { "stage": "批判性审查器", ... },
    "final_assembler":    { "stage": "最终组装器", ... }
  }
}
```

- 每一套都是一次**潜在的** LLM API 调用参数（`system_prompt` + `user_prompt` + `temperature` + `max_tokens`）。
- 真正上线时，通常只有 **④ 的输出**直接展示给用户；①②③是内部中间步骤（也可在调试 UI 里可选展示）。

### 若只想「简单一问一答」？

可以只实现 `answer_generator` 一步（很多基础 RAG 就这样）。任务书要求四阶段，是为了 **医学场景**下多加**证据审视 + 安全审查 + 终稿整合**；代价是更多 token 与延迟，换来更可控的表述。
