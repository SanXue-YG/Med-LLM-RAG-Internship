## Q1：第七阶段在整个 RAG 系统中做什么？处于什么位置？

### 一句话

**把 06 找回来的「候选文献片段」整理成「LLM 能读得下的、质量尽量高的上下文」，并准备好医学场景用的 Prompt 模板**——本周**不调用 LLM 生成答案**，只把「检索 → 生成」之间的桥梁搭好。

|-----------|---------|---------|
| **1. 上下文组装器** | 06 给你一摞「可能相关的摘要」，你要**挑、去重、控长度**，拼成一段给 LLM 看的「参考资料」 | `DocumentChunk`、`ContextAssembler` |

### 关键认知

1. **06 解决「找得准」；07 解决「喂得好」**——检索再好，若上下文重复、超长、全来自同一篇文献，LLM 也容易答偏或浪费窗口。
2. **07 仍是「准备层」，不是「生成层」**——本周代码跑通后，你得到的是 `context_text` + 填好占位符的 prompt 字符串，距离最终答案还差一步「调 LLM」。
3. **输入直接吃 06 的输出**——不需要重新查 Chroma/BM25；07 站在 06 肩膀上做后处理。

## Q2：三种输入分别是什么意思？什么时候用？

约定文档 §1 列了三种拿候选的方式，本质都是「**一组 dict，每个 dict 是一块文献片段**」，区别在**数据从哪来、排到哪一步**。

### 对照表

| 输入类型 | 代码 / 路径 | 含义 | 典型场景 |
|---------|------------|------|---------|
| **首选：`reranked`** | `result["reranked"]` | 06 流水线**跑完全程**（增强→双路召回→融合→**重排**）后的 Top-K | **正常联调、notebook 演示、最终 RAG** |
| **退化：`fused`** | `result["retrieval"]["fused"]` | 只做到**融合**，**没做** bge-reranker + 年份/期刊重排 | 调试融合策略、或 `skip_rerank=True` 时 |
| **离线：JSON 样例** | `06/.../pipeline_eval.json` → `queries[i]["reranked"]` | 把以前跑好的结果**存盘**，不连库也能测 07 | 单测、没 GPU/没全量库时、CI |

### 用流水线类比

```text
用户问题
   → 05 洗菜（query 增强）
   → 06 两路买菜（向量 + BM25）
   → 06 并菜（融合 RRF）
   → 06 摆盘（重排 rerank）     ← reranked：最终上桌的菜
   │
   │  若跳过摆盘（skip_rerank）
   ▼
   fused：并菜后的半成品，顺序未必最优

07 厨房：从「摆好盘的菜」或「并菜半成品」里，挑份量、去重复、装在一个盘里（context_text）
```

### 为什么 `reranked` 是首选？

- 每条候选带 **`final_score`**（相关性 + 时效 + 期刊等多准则加权），07 按分数**优先选高相关、再多样化**时更靠谱。
- `fused` 只有 **`fusion_score`**（两路排名 RRF 合并），**没有** cross-encoder 精排，相关顺序可能不如 `reranked`。
- 离线 JSON 与在线 `reranked` **字段结构相同**，方便「先离线开发 07，再联机 06」。

### 三种输入在代码里怎么选？

```python
# 生产 / 演示：首选
candidates = result["reranked"]

# 06 开了 skip_rerank，或你只关心融合效果
candidates = result["retrieval"]["fused"]

# 离线：读 06 已导出的评测 JSON
import json
data = json.loads(Path("06 .../pipeline_eval.json").read_text())
candidates = data["queries"][0]["reranked"]
```

## Q3：§2「单个候选的字段」——每张「卡片」上写了什么？

06 每返回一条候选，就是一个 **Python `dict`**（也可序列化成 JSON）。§2 是在说明：**07 从这张卡片里读哪些字、哪些可以当备胎**。

### 三类字段

| 类别 | 字段 | 为什么重要 |
|------|------|-----------|
| **必需（缺了不好干活）** | `chunk_id`、`text`、`doc_id` | 唯一标识、正文内容、判断是否同一篇文献 |
| **排序用（有则用，无则回退）** | `final_score`、`fusion_score`、`relevance_score`、`score` | 决定谁先进入上下文 |
| **解释 / 展示用（全进 metadata）** | `source_title`、`pub_year`、`journal`、`rerank_explain`… | 给 LLM 或用户引用、调试、多样化 |

### 常问字段逐个说

| 字段 | 通俗含义 |
|------|---------|
| `chunk_id` | 这块文字在库里的身份证号，如 `PMC524376_chunk0`（第 0 块） |
| `text` | 真正要拼进 prompt 的内容，一般是 **标题 + 摘要** |
| `doc_id` | 属于哪篇 PMC 文献；同一 `doc_id` 可能有多块（`chunk0`、`chunk1`…） |
| `source_title` | 论文标题，给人看、也给「多样化」用（别全选同一篇） |
| `source` | 从哪条路召回的：`vector` / `keyword` / `fused`（通道名，不是期刊名） |
| `final_score` | **重排后**综合分，越大越该排前面 |
| `fusion_score` | **仅融合**时的分，没 rerank 时用这个当相关性 |
| `vector_score` / `bm25_score` | 单路原始分，便于分析「语义路还是关键词路更准」 |
| `pub_year` / `journal` | 06 从 slim 元数据回查的，07 可留给 prompt 写「据 2015 年 ×× 期刊…」 |
| `token_count` | 06 估的这块多长，07 控总长时可参考 |
| `rerank_explain` | 重排为什么给这个分（调试用） |

**要点**：07 **不强制**候选带齐上表所有可选字段；有就 enrich metadata，没有也能用回退规则跑。

## Q4：§3「→ DocumentChunk 映射」——为什么要转一层？

任务书要求 07 内部用统一的数据类 `DocumentChunk`（5 个字段），而 06 吐出来的是**字段很多的大 dict**。§3 约定：**怎么从大 dict 填进小数据类**。

### 为什么不直接用 06 的 dict？

1. **接口稳定**：以后 06 多加字段，只要映射层吸收，组装器逻辑不用改。
2. **任务书字段就 5 个**：`text / metadata / relevance_score / source / chunk_id`——清晰分工。
3. **`metadata` 是「杂物抽屉」**：年份、期刊、各种 score 都收进去，不丢信息。

### 映射规则（记忆版）

| `DocumentChunk` 字段 | 从哪来 |
|---------------------|--------|
| `chunk_id` | 候选的 `chunk_id`；没有就用 `doc_id`；再没有就临时编号 |
| `text` | 候选的 `text` |
| `relevance_score` | **瀑布回退**：`final_score` → `fusion_score` → `relevance_score` → `score` → `0.0` |
| `source` | **优先文献名**：`source_title` → `doc_id` → 通道名 `source` |
| `metadata` | **剩下全部**塞进 dict |

### 两个容易混的概念

| 名字 | 含义 |
|------|------|
| 06 的 `source` | 召回**通道**（vector/keyword/fused） |
| 07 `DocumentChunk.source` | 展示/多样化用的**文献来源名**（通常是 `source_title`） |

所以 07 的 `source` **不是**简单复制 06 的 `source` 字段——同名不同义，映射表里写清楚了。

### `relevance_score` 瀑布为什么这样设计？

- 吃 **`reranked`** 时，用 `final_score`（最终排序依据）。
- 吃 **`fused`** 时，没有 `final_score`，退到 `fusion_score`。
- 吃更原始的 vector hit 时，可能只有 `score`。
- 都没有就给 `0.0`，避免组装器崩溃。

## Q5：§4「宽松兼容约定」——工程上的容错

不是为了偷懒，是为了 **单测、离线 JSON、半成品 dict** 都能跑。

| 规则 | 含义 |
|------|------|
| 输入可以是 `list[dict]` 或 `list[DocumentChunk]`，甚至混着来 | notebook 里可能已转了一部分；测试里可能只造最小 dict |
| 可选字段缺失不报错 | 按 §3 回退；缺 `pub_year` 照样组装 |
| `text` 为空或不是字符串 → **跳过** | 避免拼进空段落；在 metadata 里统计跳过了几条 |

**类比**：组装器像收简历——必填项（有正文、有 ID）才进下一轮；选填项（期刊、年份）有则加分，没有不拦人。

## Q6：§5「输出契约」——组装器交什么货？

这是 **阶段 2 要实现** 的返回形状，阶段 0 先写清楚，后面写代码和测例都对着这份契约。

```python
{
    "context_text": "...",       # 给 LLM 看的一大段参考资料（已控长、尽量在句号处截断）
    "metadata": { ... },         # 组装过程的统计账本
    "selected_chunks": [ ... ],  # 最终选中的 DocumentChunk 列表（可溯源、可 debug）
}
```

### `metadata` 里各项含义

| 键 | 含义 |
|----|------|
| `total_chunks_retrieved` | 06 一共塞进来多少条候选 |
| `unique_chunks_after_dedup` | Jaccard 去重后剩多少（去掉内容太像的重复块） |
| `chunks_selected` | 去重 + 排序 + 多样化 + 控长后，真正写进 `context_text` 的条数 |
| `estimated_tokens` | 最终上下文大概占多少 token（别超过模型窗口） |
| `chunk_sources` | 来自哪些文献/来源的分布（例如 3 篇不同 PMC、别全是一篇） |

### 和任务书 return 的对应

任务书 `ContextAssembler` 的 return 与 §5 **一致**——`context_text` + `metadata` + `selected_chunks`。本周写组装器时以 §5 为验收标准。

### 和 Prompt 模板的关系

- **`context_text`** → 填进 prompt 的 `{context}` 占位符。
- **`selected_chunks`** → 需要引用「第几条证据」时，可对照 chunk_id / source_title。
- **本周 Prompt 模板**还不消费 LLM 输出，只定义四阶段 `system_prompt` + `user_prompt_template`；真正串联在后续 LangChain RAG。

## Q7：和 06 笔记的衔接（复习用）

```text
06 RetrievalPipeline.run(query)
    │
    ├─ enhanced      → 05 的结构化 query（07 本周可不直接用）
    ├─ retrieval     → vector_hits / keyword_hits / fused（中间产物）
    └─ reranked      → ★ 07 首选输入 ★
            │
            ▼
07 ContextAssembler.assemble(candidates, max_context_tokens=...)
            │
            ├─ context_text    → PromptStage 的 {context}
            └─ selected_chunks → 可追溯证据列表
```

**记忆口诀**：06 负责 **找**；07 负责 **挑、剪、装盒**；LangChain RAG 负责 **问模型、拿答案**。
