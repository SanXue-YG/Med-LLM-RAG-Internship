## Q1：第十阶段在整个 RAG 系统中做什么？处于什么位置？

### 先用大白话说清楚（对照你的理解）

你现在的理解可以概括成四步：

> 08 让模型能按要求写答案 → 09 像「考试」给输出打分 → 10 根据考试结果和项目要求，强硬告诉模型能做/不能做 → 最后再用 09 那套考试流程复测。

**整体方向对，但有三处需要拧正：**

| 你的说法 | 对不对 | 更准确的说法 |
|---------|--------|-------------|
| 08：模型已经能根据要求输出 | ✅ 对 | 08 打通了「检索 → 组装 → 调 LLM → 出答案+引用」的完整答题链路 |
| 09：独立于回答外的「考试」，给输出评分 | ⚠️ 半对 | **评估器**确实像阅卷打分，且**不改写**模型怎么答；但 09 不止考试，还有**缓存**（同样的题少算一遍）和**批量**（一次改多份卷）。考试题主要是「正常医学问句」，看像不像参考答案、关键信息有没有漏 |
| 10：参考 09 成绩，强硬写规则提示词 | ⚠️ 半对 | 规则主要来自**本周任务书/项目安全要求**（拒答、合法引用、禁编造、格式），**不是**「看着 09 分数再改 prompt」。09 的幻觉软分最多当对照基线。而且 10 **不只**是提示词：生成后还要**机器验卷**（引用编号合不合法、章节全不全），不合格就**打回重写/修补** |
| 最后再用 09 考试流程测一遍 | ❌ 基本不对 | 10 有自己的**对抗测试**（专门出陷阱题）和自己的指标（幻觉率、引用准确率、格式合规率、拒答命中率）。可选顺带看一眼 09 的软幻觉分，但**主考不是**再跑一遍 09 的 ROUGE/缓存流程 |

#### 考试比喻（把 08 / 09 / 10 放在同一画面里）

```text
08  = 教会学生「怎么写作文」——能交卷了（answer + sources）

09  = 阅卷老师 + 档案室 + 集体阅卷
      · 阅卷：这份答案像不像标准答案？有没有漏关键点？（打分，不改卷）
      · 档案：同一题刚改过，下次直接调档，少让学生再写一遍（缓存）
      · 集体：一次发多份卷一起改（批量）

10  = 考场纪律手册 + 交卷安检 + 纪律抽考
      · 考前发纪律：找不到就写「无法回答」、不许瞎编、引用只能用发下来的文献编号……
      · 交卷安检：引用编号超范围？缺「核心答案」章节？→ 打回重写或改掉违规处
      · 纪律抽考：故意出「2025 最新疗法」「文献没写的副作用」等陷阱题，看守不守规矩
```

一句话对比：

- **09 主要回答**：「这份正常答案质量怎么样？」（以及工程上能不能少算、能不能批量跑）
- **10 主要回答**：「模型有没有按硬规矩答题？违规能不能拦下来？」（再用陷阱题验收）

所以：**09 偏「考完再打分」；10 偏「考前立规矩 + 交卷当场验 + 专门考纪律」。** 不是「09 考完 → 10 只写提示词 → 再套 09 考一遍」。

#### 用 09 真实输出看清区别（对应上表第 2 行「半对」）

来源：`09 .../outputs/samples/eval_cache_batch_report.json`（offline 样本库；query = `What is the treatment for MI?`）。

**① 模型交上来的答卷（08 生成，09 原样保留）——节选：**

> Based on the provided context: … Elevated plasma levels of homocysteine (Hcy) … The context does not provide specific treatment methods for MI. However, managing elevated Hcy levels through dietary interventions or supplements like clonidine might be considered adjunctive therapies …
>
> Evidence refs: [1] [2] [3]
>
> Sources: [1] Daily rhythms in plasma levels of homocysteine … [2] … CABG … [3] … Global Burden of Disease …

（样本库几乎没检索到真正的 MI 标准疗法文献，答案在「说没有具体治疗」之后，仍顺嘴提了饮食 / clonidine 等「可能辅助」。）

**② 09 阅卷结果长什么样（只打分、不改卷）：**

```json
"evaluation": {
  "rouge": { "rouge1": 0.072, "rouge2": 0.0081, "rougeL": 0.056 },
  "key_info_recall": 0.0,
  "key_info_missing": [
    "reperfusion", "dual antiplatelet therapy", "anticoagulation",
    "statin", "beta blocker", "ace inhibitor", "arb"
  ],
  "hallucination_risk": 0.0,
  "hallucination_signals": []
}
```

对照 `ground_truth.json`：标准答案期望的是 reperfusion、双抗、他汀等；这份答卷一个关键短语都没命中 → **recall = 0**；和参考答案文本重叠也很低 → **rouge1 ≈ 0.07**。  
同时：没有扫到「100% / completely safe」这类绝对化词 → **hallucination_risk = 0**。  
二轮同一 query：**cache.hit = true**，答案一字未改，只是少调了一次 LLM。

→ 这就是「09 像考试」的具体形态：**给分数条 + 可缓存复用；卷面内容原样不动。**

**③ 同一份答卷，10 会多做什么？（预测，尚未实装）**

| 10 模块 | 会对这份答卷做什么 | 可能结果（示意） |
|---------|-------------------|------------------|
| **ConstraintPromptBundle（考前纪律）** | 生成前写入：文献不够就输出固定拒答句；禁止添加文献未写的细节 | 模型更倾向只写「无法从现有文献回答 MI 治疗」，少写 clonidine / 饮食「可能辅助」 |
| **知识库边界（任务 a）** | 判定：上下文明确「无具体 MI 疗法」→ 应拒答 | 期望最终句接近：`Based on the provided literature, this question cannot be answered.`（或中文固定句）；而不是一边说没有、一边给建议 |
| **CitationGuard（任务 b）** | 提取 `[1][2][3]`，检查是否都在本次发放的文献编号内 | 若编号合法 → 引用校验通过；若出现 `[99]` 等 → fail → 重试/剔除 |
| **禁止编造（任务 c）** | 对照 context：clonidine 是否真被文献写成「MI 辅助治疗」 | 若属过度引申 → 视为违规倾向；靠强约束 + 对抗用例压掉（10 用规则/重试拦，不只靠 09 的软风险分） |
| **FormatChecker（任务 d）** | 查必备章节 `Core Answer` / `Evidence Summary` / `References`；缩写首次全称；参考文献是否含 title、journal、year | 当前是 `**Answer:**` / `**Evidence Summary:**` 等自由标题，且 Sources 行多半缺 journal/year → **格式不合规** → 触发重试或模板修补 |
| **对抗评测（任务 2）** | 另出陷阱题（如「2025 最新疗法」「文献未提及的副作用」）；也可把本条作「证据不足应拒答」对照 | 产出 **拒答命中率 / 引用准确率 / 格式合规率 / 幻觉率**——不是再算一遍 rouge1=0.072 |

**④ 同一例子下，09 vs 10 输出形态对比（帮助记忆）**

```text
【09 实际已产出】
result = {
  generation: { answer: 「……可能考虑 clonidine……」 , sources: [...] },  // 原样
  evaluation: { rouge1: 0.072, key_info_recall: 0.0, hallucination_risk: 0.0 }, // 只打分
  cache:      { hit: false → 二轮 true }                                  // 工程加速
}
// 结论：分数难看，但答案不会被改写；软幻觉分也没报警。

【10 预期会产出（示意）】
result = {
  answer: 「Based on the provided literature, this question cannot be answered.」,  // 可能被改写
  sources: [...],
  constraint_checks: {
    citation: { ok: true, extracted: [1,2,3] },
    format:   { ok: false → retry → ok, issues: ["missing Core Answer heading", ...] },
    boundary_hit: true
  },
  retry_count: 1,
  repaired: false
}
// 对抗报告另计：拒答命中、格式合规等 —— 主指标不是 ROUGE。
```

要点：**09 告诉你「这份卷分数很低」；10 试图让系统在证据不足时「按纪律改成拒答/合规卷」，再用另一套考题验收纪律是否生效。**

#### 本周任务书在说什么（对应上面比喻）

| 任务书 | 像什么 | 作用 |
|--------|--------|------|
| a 知识库边界 | 纪律：不会就写「无法回答」 | 防止用外部知识瞎编 |

### 一句话定位

**08 让系统「答得出」；09 在外侧「打分 / 缓存 / 批量」；10 给答题过程加「硬纪律 + 交卷安检」，并用陷阱题验收。** 本周是 RAG 的**安全约束与幻觉抑制层**，不替代 09，也不重做检索/建库。

### 端到端数据流（10 视角）

```text

    ↓ 08 LLMGenerator.generate(...)
```

### 09「软幻觉」vs 10「硬约束」——别混用

```text
09 detect_hallucination_signals（软）
  · 扫「100%」「completely safe」等绝对化措辞
  · 输出 risk 分数，便于回归对比
  · 不强制改答案、不触发拒答

10 CitationGuard + 边界拒答 + FormatChecker（硬）
  · 引用编号必须 ∈ 已提供文献
  · OOD 必须输出固定拒答句
  · 缺章节 / 缺全称 / 缺参考文献字段 → 不合规并可重试
  · 直接改变生成链路行为（prompt + 后处理闭环）
```

两者互补：09 回答「看起来像不像有风险」；10 回答「违不违规、能不能拦下来」。

### 关键认知

1. **10 仍不改变「检索增强」主路径**——找文献仍靠 05–06，装盒仍靠 07，调模型仍靠 08；10 是在生成**前后**加约束指令与校验闭环，属于**安全横切层**。
2. **与 07 Prompt 的关系是「叠加」不是「重写」**——schedule 推荐方案 A：pipeline 层注入全局 constraint system，尽量不改 07 源文件；业务四阶段模板继续负责「怎么写医学答案」。
3. **引用编号必须在组装阶段统一**——canonical 用 `[1]`/`[2]`…（对齐 08 Evidence refs）；任务书「[文献1]」可作别名。编号乱了，后面 CitationGuard 必误报。
4. **拒答是一等公民能力**——超知识库 / 诱导编造类问题，期望固定句（中英可并存），而不是「尽量回答」。这是医学 RAG 可信度的底线。
5. **重试有上限**——`max_retries` 默认 2（开发可降到 1），先修正提示重试，再规则修补；避免 Ollama 耗时失控。
6. **本阶段边界清晰**——任务书要的是强约束提示 + 校验修正 + 对抗指标，不是新索引、不是新模型、不是替代 09 的 ROUGE/缓存体系。

### 10 扩展 `result` 在系统里的意义

## Q3：`max_retries` 是什么？设为 1 和 2 有何区别？（开发备忘）

> 对应 `10 .../schedule.md`「全量 live 工程红线」：开发默认 `max_retries=1`，正式对抗再评估是否开 2。

### 含义

`max_retries` = 生成答案经 **CitationGuard / FormatChecker** 判定不合格后，**最多再让模型重写几次**（每次再调一次 LLM）。  
**不是**检索失败重试，也不是 08 四阶段内部的步数。

```text
第 0 次：正常生成 → 校验
  ├─ 通过 → 结束
  └─ 失败 → 若已用重试次数 < max_retries
              → 带上「上次哪里错了」再生成 → 再校验
              → 次数用尽 → 规则修补（repair）或带着 fail 返回
```

### 1 vs 2

| 取值 | 含义 | 最坏情况 LLM 调用次数 |
|------|------|------------------------|
| **1**（开发默认） | 首次失败后**只再生成 1 次** | 约 **2**（初写 + 1 次重试） |
| **2**（正式对抗可开） | 首次失败后最多再生成 **2 次** | 约 **3**（初写 + 2 次重试） |

- **1**：省时间。全量 live 单条本就数分钟，重试一次接近翻倍；适合调 prompt、看约束是否基本生效。  
- **2**：多一次纠正机会，拒答/引用/格式更容易被「说明错误再写」救回，但耗时与 Ollama 负载更高；报告里 `retry_count` 也会更高。

### 与 repair 的区别

| | 重试（受 `max_retries` 限制） | 规则修补（repair） |
|--|------------------------------|-------------------|
| 谁改 | 再问 LLM | 代码直接改文本（如删非法 `[99]`） |
| 成本 | 再跑一轮生成（分钟级） | 通常很快、不再完整生成 |

实现时：`retry_count` 只统计 LLM 重试；`repaired=True` 表示走过规则修补。开发期优先 `max_retries=1`，确认闭环后再对正式对抗评测开 2。

## Q4：阶段 2 里的「临时编号」`[1][2]…` 是什么意思？后期能用来回查原文献吗？

> 日期：2026-07-14。对应 `schedule.md` 阶段 2 通俗说明「发卷时给每篇文献贴临时编号」；实现见 `citation_guard.py` / 08 `format_sources`。

### 先用大白话说清楚

**「临时」不是说编号会消失**，而是说：**`[1]`、`[2]` 只在「这一次问答、这一次检索结果」里有效**，不是全库通用的文献 ID。

考场比喻：

```text
这次考试：1 号座位 = 张三的卷子
下次考试：1 号座位 = 李四的卷子
```

同理：

- 问题 A 检索到 5 段文献 → `[1]`～`[5]` 按**本次入选 chunk 的顺序**编号  
- 问题 B 检索到另一批文献 → 新的 `[1]` 可能指向完全不同的 chunk  

所以叫「临时」：**对模型写答案、对 CitationGuard 做校验很方便；但不能当作跨问题、跨会话的永久文献键。**

### `[n]` 实际指向什么？

在本工程里，`[n]` **不是** PMID / PMCID / DOI，而是：

> **本次 `selected_chunks` 列表里，第 n 个 chunk 的序号标签**

数据流：

```text
检索 → 07 组装 selected_chunks（纯文本拼接，原本无编号）
     → 10 assign_labels 按顺序贴 [1][2]…[k]
     → 08 format_sources 用同样的 index=1,2,… 生成 sources
```

代码里两处明确写了这种对齐：

- `LabeledContext` 注释：`aligned with format_sources index`（`citation_guard.py`）
- `format_sources`：`enumerate(chunks, start=1)` → `sources[].index`（`08/postprocess.py`）

另外要注意：**一个 `[n]` 对应的是一个 chunk（文献片段），不一定是一整篇论文**。同一篇 PMC 文章如果被切成多段，可能占多个编号。

### 后期想查原文，能用 `[n]` 回查吗？

#### 同一次问答内：**可以**

只要你还保留着这次 pipeline 的上下文，映射链是完整的：

```text
答案里的 [1]
  → sources 里 index=1 的那条
  → chunk_id / doc_id / source_title
  → 用 chunk_id 去 oa_comm_chunks.jsonl 查完整段落
  → 用 doc_id（pmcid）去 oa_comm_slim.jsonl 查期刊、年份等元数据
```

08 后处理已在答案末尾附了「对照表」，例如：

```text
Sources:
[1] Daily rhythms in homocysteine (doc_id=PMC520826, chunk_id=PMC520826, score=0.29)
[2] ...
```

阶段 2 还会在 chunk 上打 `metadata.citation_index`，方便 pipeline 内部把 `[n]` 解析回具体 chunk（`citation_guard._tag_chunk_index`）。

→ **`[n]` 是入口；真正用来长期定位原文的是 `chunk_id` / `doc_id`。**

#### 跨时间、跨问题：**单独一个 `[1]` 不够**

如果只保存了「模型写了见 [1]」，没有同时保存：

- 这次答案的 `Sources` 块，或  
- pipeline 返回的 `sources` JSON / `selected_chunks`

那 `[1]` 就失去了含义，无法回查。

要做长期引用或二次深挖，应使用：

| 用途 | 应使用的 ID |
|------|-------------|
| 定位具体段落 | `chunk_id` |
| 定位整篇 PMC 文献 | `doc_id`（pmcid） |
| 对外正式引用 | 标题 + 期刊 + 年份（FormatChecker `strict` 时可从 slim 回查补全） |

### 与 schedule 阶段 2 比喻的对应

| schedule 说法 | 技术含义 |
|--------------|----------|
| 发卷贴临时编号 | `assign_labels` 给本次 `selected_chunks` 贴 `[1]…[k]` |
| 交卷扫编号 | `validate` 检查答案里的 `[n]` 是否都在 `valid_ids` 内 |
| 编号与 sources 对齐 | `index=1` 的 source 就是 `[1]` 对应的 chunk |

### 一句话总结

| 维度 | 结论 |
|------|------|
| 临时编号的本质 | 本次检索结果里的 **chunk 序号标签**，方便模型引用 + 机器校验 |
| 为何叫「临时」 | 每次问答重新编号；**不是**全库永久文献 ID |
| 能否回查原文 | **同一次回答内可以**，通过 `sources` 把 `[n]` 解析到 `chunk_id`/`doc_id` 再查库 |
| 长期保存建议 | 保存 `Sources` 或 `chunk_id`/`doc_id`，不要只留 `[1]` |

阶段 4 的 `constrained_pipeline` 预期会把 `LabeledContext.selected_chunks`、`sources` 和校验结果一起打包进 `ConstrainedGenerationResult`，程序侧「从 `[n]` 追到原文」会是一条完整链路。
