## Q1：第十一阶段在整个 RAG 系统中做什么？处于什么位置？

### 先用大白话说清楚

前十周做的是「**在实验室里把医学问答能力做出来**」：

> 建库 → 检索 → 组装 → 生成 → 打分/缓存 → 加硬纪律  
> 入口基本是 **Python / Jupyter / CLI**：人坐在本机 `pipeline.run(query)`。

本周开始做另一件事：把这套能力**端出去给人（或别的程序）用**——用 **HTTP API** 包一层，让外部客户端用 `POST /api/v1/qa` 就能问，而不必 import 各阶段源码、也不必开 Jupyter。

对照记忆：

| 阶段段 | 在干什么 | 入口形态 |
|--------|----------|----------|
| 01–04 | 离线：数据与向量库 | 脚本 / notebook |
| 05–08 | 在线：检索 + 生成「答得出」 | Python `pipeline.run` |
| 09 | 外侧：打分 / 缓存 / 批量 | CLI + notebook |
| 10 | 横切：硬纪律 + 交卷安检 | Python 约束流水线 |
| **11（本周）** | **服务化：统一协议 + 问答接口** | **FastAPI（HTTP / SSE）** |

一句话：

> **01–10 解决「系统会不会答、守不守规矩」；11 解决「别人怎么稳定地调用这套系统」。**  
> 本周是 RAG 的 **服务接入层 / API 外壳**，**不重做**检索、生成或约束内核。

### 餐厅比喻（把 08 / 10 / 11 放在同一画面里）

```text
08  = 后厨已经会做菜（检索 → 组装 → LLM → answer + sources）

10  = 后厨加了食品安全与出品规范（拒答、合法引用、格式安检、不合格打回）

09  = 品控抽检 + 出餐记录复用 + 批量备餐（外侧评估 / 缓存 / 批量；本周可不挂）

11  = 前台点餐系统
      · 统一菜单格式（ResponseModel：code / message / data / request_id）
      · 点错菜有标准拒单话术（错误码 + 全局异常）
      · 健康检查：后厨是否还活着（/health；可选探 Ollama）
      · 同步出整盘菜（POST /qa）或边做边上（POST /qa/stream · SSE）
      · 可选：同一桌连点几道，带上桌号 session_id（会话关联）
      · 每单记流水：单号、耗时、成败（问答调用日志）
```

要点：**11 不换菜谱、不改建库**——默认把 10 的约束流水线（可回退 08）接到 HTTP 上，让「点餐 → 出餐」变成可对接的服务。

### 本周任务书在说什么

| 任务书 | 像什么 | 作用 |
|--------|--------|------|
| **1. FastAPI 骨架** | 开店：统一小票格式、错误码、异常处理、日志、探活 | 没有骨架，后面接口会各写各的、难维护 |
| 统一 `ResponseModel` + 分页模型 | 所有成功/失败都长一个样 | 前端/调用方只认一种信封 |
| 错误码（1001 / 2001 / 3001 / 4001…） | 拒单原因分类 | 参数错 ≠ 模型挂 ≠ 文档不存在 |
| 全局异常处理 | 后厨炸锅也返回标准错误体 | 避免裸 500 堆栈甩给客户端 |
| 日志 + `/health` | 流水账 +「店开着吗」 | 运维与联调入口 |
| **2. 问答接口** | 真正点餐口 | 把 RAG 接到网络 |
| 同步 `/qa` | 等整盘上齐再给 | 简单集成、完整 JSON |
| 流式 `/qa/stream` | 边做边上（SSE） | 降低首字等待感 |
| 集成 RAG 流水线 | 前台叫后厨 | 默认 10 约束管线 |
| `session_id` 会话 | 同桌连点，带上前文 | 多轮；首版可内存 Store |
| 参数校验（query / top_k） | 空盘、离谱份量直接拒 | 对应错误码 1001 |
| 调用日志（request_id、耗时、状态） | 每单可追溯 | 为后续统计/排障打底 |

### 关键认知

1. **11 是「接入层」，不是「又一个 RAG 算法周」**——质量与安全仍分别靠 08/09/10；本周交付的是可调用的服务边界。
2. **默认内核应挂 10，而不是裸 08**——对外服务应带上已验收的约束护栏；08 作可配置回退即可。
3. **统一响应 + 错误码是骨架的核心价值**——比「先写一个能跑的 `/qa`」更优先：没有标准信封，后续前端/统计都会返工。
4. **会话是「关联」，不是「重做多轮 RAG」**——首版内存 Store + TTL + `max_turns` 即可满足任务书；持久化/分布式属后续。
5. **流式可以真流式或伪流式**——体验目标是 SSE 事件约定清晰；Ollama/生成器未就绪时，降级策略要写进文档，避免验收口径含糊。
6. **开发默认 sample / 预热，避免每次冷启打满 610 万**——与 10「规则用 fixture、live 克制」同理；`full` 需显式打开。
7. **本阶段边界**：不做真实鉴权（预留 2001）、不做前端、不做 Docker 生产编排——那些是服务化后续或运维范围。

## Q3：开发默认 sample，若要验证「全量上的效果」怎么做？要用哪些 Dataset？

> 日期：2026-07-23。对应 schedule「开发默认 `retrieval_mode=sample`」；全量验证**非本周主轨**，先记在笔记，阶段 5 若真要跑再拷进 schedule。

### 先分清：你在验什么

| 验证目标 | 用 sample 够不够 | 要不要全量 |
|----------|------------------|------------|
| HTTP 信封、错误码、会话 Store、伪流式 SSE、调用日志 | ✅ 够（mock / sample） | 否 |

### 开关怎么打（实现时按此设计）

进程级配置（**不要**每个请求换 mode）：

```text

# 收尾全量抽检时（二选一即可）
retrieval_mode = "full"            # 改 app/config.py 或环境变量后重启 uvicorn
# 例：MED_RAG_RETRIEVAL_MODE=full   （若实现时增加该 env）
```

Notebook / 联调建议：

```text
C0.5 或阶段 5 增补单元：
  1) 资源自检 ready（见下表）
  2) 临时服务（或 TestClient）retrieval_mode=full
  3) POST /qa 仅 1–2 条熟悉 query（如 metformin cardiovascular effects）
  4) 确认：200 + answer/sources + 日志有 request_id；可选看 constraint_checks
```

工程红线（对齐 10 全量 live）：

1. **禁止**每条请求 `from_mode("full")` 重建（Chroma/BM25/reranker 极慢）→ 进程内**单例** pipeline。

## Q4：什么是「伪流式 SSE」和「真 token 流」？（对照报告用语）

> 日期：2026-07-23（2026-07-25 按报告用语补强）。  
> 对应：[`schedule.md`](../11%20服务化与接口开发第一部分/schedule.md) MVP 伪流式；报告 [`服务化接口报告.md`](../11%20服务化与接口开发第一部分/docs/服务化接口报告.md) §3.1「同步 QA + **伪流式 SSE** | Ollama **真 token 流**…」。

### 报告那句话在说什么

| 已交付 | 未交付（后续） |
|--------|----------------|
| 同步 QA + **伪流式 SSE** | Ollama **真 token 流**（将来 `stream_mode` 可从 `pseudo` 扩成 `token`） |

二者不是两套无关接口，而是同一路径 `POST /api/v1/qa/stream`（都走 **SSE**）上的**两种实现深度**：

- **伪流式（现在有）**：整条 RAG/约束跑完 → 再把最终 `answer` 切块，用 SSE 的 `token` 事件推出去。  
- **真 token 流（还没有）**：Ollama **每生成一小段字**就立刻通过 SSE `token` 推出去。

`meta.stream_mode`（及响应头 `X-Stream-Mode`）标明当前是哪种：现网固定 **`"pseudo"`**。

### 先分清三个词

| 词 | 是什么 | 本周 |
|----|--------|------|
| **SSE** | 传输协议：`text/event-stream`，事件如 `meta` → `token*` → `done` | ✅ |
| **伪流式（pseudo）** | 实现策略：内容一次生成完，再「假扮」分段推 | ✅ MVP |
| **真 token 流** | 实现策略：Ollama `stream=true`，模型增量 = SSE `token` | ❌ |

口诀：**SSE 是水管；伪/真流是水怎么灌进水管的。**

### 流式接口在解决什么问题

同步 `/qa`：等整段算完才给一个 JSON。  
流式 `/qa/stream`：希望边出字边上屏（或至少前端按流式协议接线）。  
「字是不是模型刚吐出来的」→ 取决于伪还是真，不取决于「用了没有 SSE」。

### 真流式 vs 伪流式（大白话）

| | **真 token 流** | **伪流式 SSE（本周）** |
|--|-----------------|------------------------|
| 模型侧 | Ollama **一边生成一边吐字**（`stream=true`） | 仍 **`stream=false` 整段生成完** |
| API 侧 | 模型增量 → 立刻 `event: token` | 整段 `answer` → 按句/窗口切开再连发 `token` |
| 用户体感 | 生成一开始就可能看到字 | **前面干等**（≈ 同步总时长），然后字**很快刷完** |
| 与 10 约束 | 难：半截已上屏，重试不好撤回 | **易**：先完整 `run`（含校验/重试），再推最终答案 |
| `stream_mode` | 规划 `"token"` | 现网 **`"pseudo"`** |

餐厅比喻：真 token 流 = 炉上炒一句端一句；伪流式 = 整盘安检完再切小块一道道端（桌上仍是分段上菜，厨房并未边炒边递）。

时间线对比：

```text
【真流式】
Client ──请求──► 开始生成 ─t1─t2─t3─…─► 结束
                 ▲推 ▲推 ▲推

【伪流式 MVP】
Client ──请求──► ……完整 retrieve+generate+guards…… ──► 再切块推 t1 t2 t3 … done
                 |←———— 和同步 /qa 差不多长的等待 ————→|
```

所以：伪流式**主要交付的是「流式 API 形态 + SSE 事件约定」**，方便前端先接聊天式 UI；**不保证**首字更早出现。产品文案不宜在 `stream_mode=pseudo` 时宣传「实时流式生成」。

### 前端怎么识别

1. 读 `meta.stream_mode` 或头 `X-Stream-Mode`。  
2. `pseudo`：`meta` 后可能长时间无 `token` → 显示「正在检索/生成…」，别当断连。  
3. 所有 `token.text` 拼接应等于 `done.answer`。  
4. 以后若上真流：尽量保持事件名不变，只改 `stream_mode` 与延迟语义。

### 「08 硬编码 `stream=False`」具体指什么

在 `08 .../src/llm_generator.py` 的 `generate()` 里，发给 Ollama `/api/chat` 的 JSON **写死了**：

```python
payload = {
    ...
    "stream": False,   # ← 这里
    ...
}
resp = self._get_client().post("/api/chat", json=payload)
# 等整份响应 JSON 回来，取出 message.content 整段字符串
```

含义：

1. **请求层**：明确告诉 Ollama「别流式，一次给完整答案」。  
2. **代码层**：用普通 `post` + `resp.json()`，**没有**按行读 NDJSON / 迭代器消费增量。  
3. **接口层**：没有 `generate_stream()` 之类方法；10 的 `ConstrainedGenerationPipeline` 也只调同步 `generate` / `generate_json`。

所以不是「Ollama 不支持流式」，而是**当前工程封装选择了非流式**，且上面叠了多步生成 + 约束重试——本周若强做真流式，等于同时改 08 + 重做 10 的流式闭环，范围过大。

### 为何 schedule 定稿「MVP = 伪流式」

1. 任务书要的是**流式接口**（同步 + 流式两种响应模式）——伪流式也能用 SSE 满足契约与联调。  
2. 真流式与 **10 交卷安检/重试** 冲突大：中途推出去的字，重试后可能整段作废。  
3. 伪流式与同步共用同一条 `rag_service.answer()`，`done` 里的 sources / `constraint_checks` 与 `/qa` **一致**，验收简单。  
4. `meta.stream_mode: "pseudo"` 写进事件，避免调用方误以为已是 token 级真流。

### 以后若要真流式，大概要动哪

| 步骤 | 内容 |
|------|------|
| 1 | 08 增加 `generate_stream`：`stream=True` + 逐块 yield |
| 2 | 决定：只对流式路径跳过/简化多步与重试，还是「先流式草稿、结束再校验」 |
| 3 | 11 SSE 把增量映射为 `token`；失败时发 `error`（已推内容的 UI 策略另定） |

本周**不阻塞**验收；需要时再开专题。

## Q5：会话「持久化后续」能否复用 09 预留的本地化存储接口？

> 日期：2026-07-23。对应 schedule「会话存储…持久化后续」与 09 schedule「阶段 3 接口预留」/`BaseCacheBackend`。

### 先纠正：你标的那段主要不是「会话落盘」

[`09/.../schedule.md`](../09%20生成答案评估，缓存策略与批量处理/schedule.md) **阶段 3 接口预留**里的：

| 组件 | 实际用途 |
|------|----------|
| `GenerationRequest` / `GenerationResponse` | 统一「生成请求/响应」数据结构 |
| `ModelAdapter`（Protocol） | **多模型/多后端生成**的标准口：`generate(request) -> response` |
| `PipelineModelAdapter` | 把现有 `pipeline.run(query)` 包成上述接口 |
| `SnapshotModelAdapter` | 用 08 快照冒充生成（offline） |

→ 这是 **生成适配器（怎么叫模型）**，不是 **会话历史存哪**。  
和 11 的 `SessionStore(session_id → 多轮 Q/A)` **不是同一类对象**。

### 09 里和「持久化」更接近的是缓存后端预留

| 组件 | 状态 | 存什么 |
|------|------|--------|
| `GenerationCache` + 进程内 LRU/TTL | ✅ 已用 | **相同 query+context+model… 的生成结果**，少调 LLM |
| `BaseCacheBackend` / `MemoryCacheBackend` | 接口已留；sqlite/redis **未实现**；`cache_backend` 配置键**未真正接线** | 仍是**答案缓存**，不是对话 session |
| `config.cache_backend` | 预留 `memory` → 未来 `sqlite`/`redis` | 同上 |

报告原文也写了：持久化缓存后端「本阶段未完整实现」。

### 和 11 会话持久化的关系：能借鉴模式，不能直接当 SessionStore

```text
09 GenerationCache          11 SessionStore（计划）
─────────────────          ─────────────────────
键：hash(query,context,…)   键：session_id
值：某次生成结果             值：多轮 turns[{query,answer,…}]
目的：少算、加速             目的：多轮关联、可回看
生命周期：TTL / LRU         生命周期：TTL / max_turns
```

| 问题 | 结论 |
|------|------|
| 能否 `import BaseCacheBackend` 当会话库直接用？ | **不适合直接当 SessionStore**：键值语义、读写 API（get/set by cache key vs append turn）都不匹配 |
| 有没有可复用的？ | **模式可复用**：`Protocol` + 内存实现 + 日后 sqlite；`PipelineModelAdapter` 可给 11 `rag_service` 包 10/08 作参考 |
| 本周要不要接 09 持久化缓存？ | **不必**：schedule 已定会话首版内存；09 缓存挂 `/qa` 也非本周必做 |
| 「持久化后续」建议落点 | 11 自建 `SessionStore` 后端接口（如 `MemorySessionStore` → 日后 `SqliteSessionStore`）；若同时要跨重启复用**答案**，再接线 09 `BaseCacheBackend` |

### 对 11 的实用建议

1. **本周**：内存 `SessionStore` 即可，完成任务书「关联历史」。  
2. **设计时**：预留 `Protocol`（对齐 09 习惯），别把 dict 写死在路由里。  
3. **若要加速重复问答**：可选挂 09 `GenerationCache`（答案缓存）——与会话持久化是两条线。  
4. **`ModelAdapter`**：适合 `rag_service` 屏蔽 10/08 差异，**不解**会话落盘问题。

### 一句话

09 预留的是 **「怎么统一调用生成」**（`ModelAdapter`）和 **「答案缓存以后怎么落到 sqlite」**（`BaseCacheBackend`），不是现成的会话数据库。11 会话持久化应自建 Store 后端；可抄 09 的接口分层，**不要**误以为接上 `ModelAdapter` 就等于会话持久化。

### 为什么 `/` 看起来是白屏？

根路径 **故意返回 JSON 信封**，不是 HTML：

```text
GET /  →  Content-Type: application/json
{
  "code": 0,
  "message": "ok",
  "data": { "service": "medical-rag-api", "stage": "5-done", ... },
  "request_id": "...",
  "timestamp": "..."
}
```

Chrome 对纯 JSON 有时几乎像空白页，只在角落出现 **Pretty-print** 勾选（你截图里的那种）。勾上 Pretty-print，或看「查看网页源代码 / 开发者工具 Network → Response」，就能看到完整 JSON。终端已有 `GET / … 200 OK`，说明响应成功。

对照：

| URL | 你看到什么 | 实际是什么 |
|-----|------------|------------|
| `/` | 易被当成「空白网站」 | **JSON 元信息**（服务名、stage、mode） |
| `/docs` | Swagger 文档页（有按钮可试接口） | FastAPI **自动生成的 API 调试 UI**（仍不是产品前端） |
| `/health` · `/ready` | 也是 JSON | 探活 / 就绪 |
