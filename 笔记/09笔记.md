### 端到端数据流（09 视角）

```text
用户 query（英文）
    ↓ cache lookup(key = hash(query, context_text, model, temperature))
    ├─ HIT  → 取缓存 generation result
    └─ MISS → 08 MedicalGenerationPipeline.run(query)
              ↓ 若 temperature ≤ 阈值且成功 → cache.set(...)
    ↓ 09 AnswerEvaluator.evaluate(generated_answer, ground_truth_entry)
              ↓ rouge / key_info_recall / hallucination_risk / readability
    ↓ 汇总 { generation, evaluation, cache: { hit, key, stats } }

批量路径：
list[query] → BatchRunner.run_batch()
    → 每任务走上述 cache + pipeline + evaluate
    → list[result]（顺序与输入 queries 对齐）
```

### 一图看懂：串行和并行到底在说什么

```text
单条 query（内部流程）：
Q1
  └─ cache lookup
      ├─ HIT  -> 直接返回
      └─ MISS -> 08 生成链（按顺序）-> 评估 -> 返回

多条 query（批量流程）：
顺序模式（08脚本默认）：
Q1 -> Q2 -> Q3 -> Q4

并行模式（09 BatchRunner 可选）：
Q1 ----\
Q2 -----+--> 同时执行（每条内部仍是“先cache，再决定是否调LLM，再评估”）
Q3 -----+
Q4 ----/
```

要点：**并行是“多条问题之间并行”，不是“一条问题内部四个阶段并行”。**

### 按当前计划，后续如何落地「查答案 + 少重复写 + 批量更快」

下面对应 `schedule.md` 的阶段 0–5，完成后你会看到很直观的阶段成果。

1. **阶段 0（先把“对照标准”准备好）**  
   先建 `ground_truth.json`（4 条 query 的参考答案 + key phrases），并在 notebook C0 加载校验。  
   结果：后面的“查答案质量”有了统一标尺。

2. **阶段 1（实现“查答案”）**  
   完成 `AnswerEvaluator`，在 notebook C1 演示 ROUGE、关键信息召回、幻觉信号、可读性。  
   结果：每次生成后都能得到一份结构化质量报告，而不是只看主观感觉。

3. **阶段 2（实现“少重复写”）**  
   完成 `GenerationCache`（key=query+context+model+temperature，含 TTL 和低温门控），在 C2/C3 做 miss→hit、过期、高温不缓存演示。  
   结果：同样输入第二次基本不再调 LLM，速度提升且省调用成本。

4. **阶段 3（实现“批量更快”）**  
   完成 `BatchRunner`，用线程池并行跑多条 query；单条失败不影响其他条，并保持输出顺序一致，在 C4 验证。  
   结果：一次跑 4 条评测 query 的总耗时明显下降。

5. **阶段 4（把三件事真正串起来）**  
   完成 `pipeline_with_eval.py`，统一输出 `{generation, evaluation, cache}`，在 C5 跑 08 的四条基准 query 做汇总。  
   结果：形成可直接复用的“生成+评估+缓存”一体化接口。

6. **阶段 5（收尾导出与复现）**  
   C6 导出 `eval_cache_batch_report.json`，CLI 脚本做 notebook 等价复跑。  
   结果：有可提交的样例报告与可重复执行入口。

### 关键认知

1. **09 不改变 RAG 的「检索增强」核心路径**——检索、组装、Prompt、LLM 生成仍由 05–08 负责；09 是在 `run()` **外侧**加评估器、缓存器和批量调度器，属于**横切关注点**（cross-cutting concern）。
2. **评估的是「生成答案」，不是「检索质量」**——06 的 `pipeline_eval.json` 评的是 Top-K 命中；09 评的是 08 产出的 `answer` 文本是否忠实、完整、安全。两者互补，不可混用。
3. **缓存键必须含 `context_text`**——同一 query 若检索结果变化（索引更新、mode 切换 sample↔full），context 不同则不应命中旧缓存；schedule 已把 `model_name` 和 `temperature` 纳入键，设计合理。
4. **幻觉检测是启发式规则，不是事实核查**——任务书的「研究表明」「100%」「完全安全」等信号，与 08 `critical_reviewer` 的 LLM 审查互补：09 提供**可重复、零成本**的规则分，便于批量对比与回归测试。
5. **ground truth 需人工整理**——08 `generation_eval.json` 只有生成快照，没有标准答案；本周要先为 4 条 query 手写 `reference_answer` + `key_phrases`，ROUGE 与 recall 才有意义。
6. **本阶段边界清晰**——任务书要的是评估器 + 进程内 LRU 缓存 + 可选线程池批量，不是人工标注平台、不是 Redis、不是在线 A/B 实验框架。

### 09 扩展 `result` 在系统里的意义

| 字段 | 谁用 | 作用 |
|------|------|------|
| `generation` | 与 08 兼容 | 原 `MedicalGenerationPipeline.run()` 返回值 |
| `evaluation.rouge` | 评测 / 回归 | 与 `ground_truth.reference_answer` 的文本重叠度 |
| `evaluation.key_info_recall` | 医学场景重点 | 剂量、时间、副作用等关键信息是否覆盖 |
| `evaluation.hallucination_risk` | 安全审计 | 绝对化表述风险分，可设阈值告警 |
| `evaluation.readability` | 用户体验 | 句长、句数等可读性粗指标 |
| `cache.hit` / `cache.stats` | 性能优化 | 二次同 query 是否跳过 LLM；命中率统计 |
| `error`（批量时） | 容错 | 单条失败不中断整批，便于大批量评测 |

### Q4-1：`ROGUE` 是什么？如何评估文本相似性？它和缓存有什么关系？

**先纠正术语**：任务书里写的 `ROGUE` 基本可以视为 **`ROUGE`** 的笔误。  
`ROUGE`（Recall-Oriented Understudy for Gisting Evaluation）是常见的文本重叠指标，用来比较“生成答案”与“标准答案”的相似度。

**在本周怎么用**（按计划）：

- 用 `rouge-1 / rouge-2 / rouge-L`（通常看 F1）。
- 输入：`generated_answer` vs `ground_truth.reference_answer`。
- 含义：看关键词、短语、句式结构是否覆盖到标准答案核心内容。

**它的作用**：

1. 给答案质量一个可量化分数（不是只靠主观阅读）。
2. 用于回归对比（改 prompt/参数后是否变好）。
3. 作为“查答案”中的一个维度，和 key_info_recall、幻觉风险一起看。

**它和缓存的关系**：

- **不是**直接用来做缓存命中判断。
- 缓存命中看的是“输入是否同一问题场景”（query + context + model + temperature）。
- ROUGE 是“输出质量评估”，缓存是“避免重复计算”。
- 两者在 09 阶段是并列能力：一个管质量，一个管性能。

### Q4-2：如何评估“关键信息是否来自标准答案”？如何保证来源和准确性？

任务书要求的是：`recall = overlap / gt_matches`。  
按当前计划，落地方式是“**标准答案关键短语表 + 生成答案匹配**”。

**具体做法**：

1. 在 `ground_truth.json` 为每条 query 维护：
   - `reference_answer`
   - `key_phrases`（剂量、时间范围、安全信息、机制词等）
2. 对生成答案做正则和短语匹配，得到 `predicted_key_phrases`。
3. 计算与 `key_phrases` 的交集，得到 `key_info_recall`。

**如何判定“来自标准答案”**：

- 工程上是按“短语/模式重叠”判定（即 overlap），不是语义级因果证明。
- 也就是说：它能判断“标准答案中要求的关键点是否被覆盖”，但不能 100% 证明“模型一定从正确证据链推导而来”。

**准确性保障边界（很重要）**：

- 09 的这套是“自动评估近似方法”，不是医学事实终审。
- 更稳妥做法是联合：
  - 08 的 `sources` / 引用结果
  - 09 的 key_info_recall + 幻觉风险
  - 必要时人工 spot check

### Q4-3：`无依据的绝对化表述` 如何判断？如果论文本身就很绝对会不会误报？

当前计划是**启发式风险信号**，不是法庭式真伪裁决。  
例如匹配到“100%”“completely safe”“has been proven”等词，会加风险分。

**如果引用的原论文中明确说明了相关信息但它的表述显得较为绝对，在此处是否会被列为高风险？会。**

- 如果原论文确实这样写，而模型也复述了绝对语句，规则仍可能标高风险（这是可预期的误报）。
- 原因：这套规则是在做“安全提醒”，宁可保守一点，也不直接判真。

**怎么降低误报**（计划内可做）：

1. 把它定义为 `risk signal`，不是 `hallucination verdict`。
2. 与引用信息联动解读：有明确来源时降低严重等级，而不是直接判错。
3. 规则加权：绝对词 + 无引用时权重高；绝对词 + 有来源时权重低。

结论：该指标用于“筛查风险段落”，不是单独定生死。

### Q4-4：缓存怎么实现？存哪里？TTL 多长怎么定？

按当前 schedule，首版是：**进程内 LRU + TTL**（内存缓存）。

**实现形态（本周）**：

- 存储位置：当前 Python 进程内存（不是云端数据库）。
- 生命周期：进程结束缓存失效（除非后续扩展落盘）。
- 键：`hash(query + context_text + model + temperature)`。
- 策略：只缓存低温度、成功生成的结果；超 `max_entries` LRU 淘汰；过期 TTL 删除。

**未来可扩展**：

- 本地持久化：SQLite / JSON / diskcache
- 服务化：Redis（本机或云端）
- 再进一步：多实例共享缓存（线上部署）

**TTL 怎么定**（建议口径）：

- 开发验证期：先用 `24h`（便于复现实验且避免太旧）。
- 稳定后可按任务改成 `24h~7d` 可配置。
- 医学内容建议保守：宁可短一些，并支持 `force_refresh=True` 强制重算。

所以本周是“最小可行缓存（MVP）”，先解决重复调用和可控时效，再决定是否升级为持久化/云端缓存。

### Q4-5：并行发生在哪？单问题四阶段会并行吗？CPU 核心数怎么定？

并行发生在**多 query 批处理层**，不是单 query 内部四阶段。

**正确理解**：

- 单个问题：仍按 08 的流程串行执行（前一步结果给后一步）。
- 多个问题：09 的 `BatchRunner` 可把 Q1/Q2/Q3/Q4 同时发起（可选）。

所以不是“每个 stage 并行再跑一次 LLM”，而是“多个问题各自跑自己的完整链路”。

**`max_workers` 如何按 CPU 调整**（本周建议）：

1. 以保守为主：`max_workers = min(4, os.cpu_count() or 1)`（与 schedule 一致）。
2. 若 Ollama 排队/超时明显：降到 2。
3. 若机器空闲且稳定：可尝试 3~4。

注意：这里虽然提到 CPU 核数，但真实瓶颈常在本地 LLM 推理与 I/O，不是纯 CPU 计算；因此要结合实测延迟和失败率动态调。
