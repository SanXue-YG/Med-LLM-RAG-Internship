## Q1：第六阶段在整个 RAG 系统中做什么？处于什么位置？

### 一句话

**把「用户问题」变成「排序好的相关文献片段列表」**——在 04 建好的向量库和 03 的文本块之上，用**多路召回 + 融合 + 重排序**把检索质量做上去，为后续 LLM 生成答案准备好 Context。

## Q2：05 和 06 怎么衔接？`EnhancedQuery` 里什么字段会被用到？

### 数据流

```text
用户: "What is the treatment for MI after 2015?"
        │
        ▼  MedicalQueryEnhancer.process()
EnhancedQuery:
  original          →  日志 / 展示
  vector_query      →  06 向量路 → 04 encode_queries() → Chroma query
  keyword_query     →  06 BM25 路 → 分词 → BM25 top_k
  filters           →  06 向量路 where_filter（executable=true 的项）
                      →  06 重排 recency（year_* 解析结果，检索后特征）
  expanded_terms    →  已在 keyword_query 中体现
  entities          →  调试 / 可解释性
        │
        ▼  MultiPathRetriever.retrieve(query_info, ...)
融合候选 list[dict]
        │
        ▼  Reranker.rerank(query, candidates, ...)
最终 Top-K（含 score、解释字段）
```

### 字段用途表

| `EnhancedQuery` 字段 | 06 谁用 | 说明 |
|---------------------|---------|------|
| `vector_query` | 向量召回 | 交给 04 `ChromaIndexBuilder.query()`；BGE 前缀由 04 加，06 不重复 |
| `keyword_query` | BM25 召回 | 已去停用词、含同义词扩展，适合词匹配 |
| `filters` + `chroma_where()` | 向量召回 | 仅 `executable=true` 的进 Chroma（如 `strategy=sliding_window`） |
| `filters`（`year_*`） | 重排序 recency | `executable=false`；从 02 slim 按 `doc_id` 回查 `pub_year` 打分 |
| `original` / `cleaned` | 重排序 relevance | reranker 的 query 文本通常用清洗后的原句 |

## Q3：任务书三条要求分别是什么意思？

任务书 `任务.txt` 共三块，对应 schedule 阶段 1–4。

### 3.1 任务一：多路检索（MultiPathRetriever）

**目标**：不只靠一种检索方式，而是**两路并行召回**，再合并，弥补单一方法的短板。

| 子任务 | 含义 | 为什么需要 |
|--------|------|-----------|
| **向量检索** | query → 嵌入向量 → Chroma 近似最近邻 Top-K | 擅长**语义相似**（同义改写、概念相关）；04 已建好库 |
| **BM25 关键词检索** | query 分词 → 在 chunk 全文上算 BM25 分 → Top-K | 擅长**精确词匹配**（药名、基因名、缩写展开后的词） |
| **构建 BM25 索引** | 读 03 chunks JSONL，建倒排 + 统计量 | BM25 不走 Chroma，需**单独索引**（语料 = chunk 的 `text`） |
| **融合策略** | 把两路排名合成一份列表 | 两路 Top-K 往往重叠又不完全相同，需要规则合并 |

**类比**：向量检索像「懂意思的图书管理员」；BM25 像「按关键词查卡片目录」；融合是「把两份推荐名单合成一张」。

### 3.2 任务二：重排序器（Reranker）

**目标**：融合后可能有几十条候选，**顺序还不够准**；用更强的模型对「query–文档对」逐条打分，把最相关的排到前面。

| 概念 | 含义 |
|------|------|
| **Bi-Encoder（04 BGE 嵌入）** | query、文档**分别**编码成向量，用距离比相似度；快，适合百万级召回 |
| **Cross-Encoder（bge-reranker-base）** | query 和文档**拼在一起**送进分类模型；慢，但更准；只适合对**少量候选**（如 30→10） |
| **多准则重排** | 不只看 relevance，还加权 **recency**（年份越新分越高）、**authority**（期刊权重） |

任务书示例权重：

```python
criteria_weights = {
    "relevance": 0.6,   # reranker 语义相关分
    "recency": 0.25,    # 时效性（来自 02 slim 的 pub_year）
    "authority": 0.15,   # 期刊权威性（规则表）
}
```

**注意**：年份/期刊不在 Chroma metadata 里（见 05 笔记 Q1），所以 **recency/authority 在检索之后、用 doc_id 回查** 再做特征分，而不是重建 04 索引。
回查采用 \06 检索系统开发第二部分\data\oa_comm_slim.jsonl （已从外部盘复制到本地）

### 3.3 任务三：完整检索流水线

**目标**：把 05 + 06 串成一条可演示、可评测的链路：

```text
query → enhancer → multipath retrieve → fuse → rerank → Top-K JSON
```

交付形态：`pipeline.py` + `notebooks/retrieval-pipeline.ipynb` + `scripts/run_retrieval_eval.py`。

## Q4：三种融合策略分别是什么？该默认用哪个？

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **simple** | 两路结果合并，按 `chunk_id` 去重 | 实现最简单 | **丢掉排名信息**——排第 1 和排第 20 一视同仁 |
| **rrf**（Reciprocal Rank Fusion） | 按名次算 `1/(k+rank)` 再相加（常用 k=60） | 不依赖两路分数尺度，**学术检索常用** | 需调 k；对极端分数不敏感 |
| **weighted** | 两路分数归一化后加权求和（向量权重大） | 可强调语义路 | 两路分数分布不同，归一化要小心 |

**本工程默认**：`rrf`（schedule 共识）；`weighted` 作备选对比。

## Q7：和 04「只有一种向量检索」相比，06 提升了什么？

| 维度 | 仅 04 向量 Top-K | 06 完整检索链 |
|------|-----------------|---------------|
| 召回 | 语义相近 | 语义 + 关键词，**漏召回更少** |
| 排序 | 向量距离一次定序 | 融合后再 **cross-encoder 精排** |
| 医学 query | 缩写/药名可能偏弱 | 05 扩展 + BM25 补精确匹配 |
| 时效/期刊 | 无 | recency / authority 可调权 |
| 时延 | 低（~十几 ms 量级 query） | 更高（BM25 建索引 + reranker 推理） |

**代价**：工程复杂度、内存（BM25）、推理时间（reranker）。典型做法：向量/BM25 各取 Top-20，融合后取 Top-30 再 rerank 到 Top-10。

## Q10：三种融合策略：要做什么、怎么选？

**阶段 2 的计划是：三种都实现，但默认用其中一种。**

| 层面 | 说明 |
|------|------|
| **代码** | `fusion.py` 提供 `simple` / `rrf` / `weighted` 三个可切换接口（任务书里的 `fusion_strategy` 参数） |
| **默认** | schedule 已定 **`rrf` 为主策略**（学术检索场景较稳） |
| **对比** | 会用 schedule 里那 **5 条验证 query** + 少量人工标注（schedule 提到 MRR/nDCG 小样本）做**定性/粗定量对比**，看排序是否合理 |
| **最终选择** | **不是**跑一大套 benchmark 只留一个、删掉另外两个；而是：**默认 rrf 上线**，notebook/CLI 里能切换三种策略做对比，必要时再调默认 |

所以：三种都会实现并**可对比**，但工程上更像「可配置 + 有默认」，而不是「三选一淘汰赛」。
