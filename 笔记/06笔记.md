## Q1：第六阶段在整个 RAG 系统中做什么？处于什么位置？

## Q2：05 和 06 怎么衔接？`EnhancedQuery` 里什么字段会被用到？

### 数据流

```text
用户: "What is the treatment for MI after 2015?"
        │
        ▼  MedicalQueryEnhancer.process()
EnhancedQuery:
  original          →  日志 / 展示
  vector_query      →  06 向量路 → 04 encode_queries() → Chroma query
  keyword_query     →  06 BM25 路 → 分词 → BM25 top_k
  filters           →  06 向量路 where_filter（executable=true 的项）
                      →  06 重排 recency（year_* 解析结果，检索后特征）
  expanded_terms    →  已在 keyword_query 中体现
  entities          →  调试 / 可解释性
        │
        ▼  MultiPathRetriever.retrieve(query_info, ...)
融合候选 list[dict]
        │
        ▼  Reranker.rerank(query, candidates, ...)
最终 Top-K（含 score、解释字段）
```

### 字段用途表

| `EnhancedQuery` 字段 | 06 谁用 | 说明 |
|---------------------|---------|------|
| `vector_query` | 向量召回 | 交给 04 `ChromaIndexBuilder.query()`；BGE 前缀由 04 加，06 不重复 |
| `keyword_query` | BM25 召回 | 已去停用词、含同义词扩展，适合词匹配 |
| `filters` + `chroma_where()` | 向量召回 | 仅 `executable=true` 的进 Chroma（如 `strategy=sliding_window`） |
| `filters`（`year_*`） | 重排序 recency | `executable=false`；从 02 slim 按 `doc_id` 回查 `pub_year` 打分 |
| `original` / `cleaned` | 重排序 relevance | reranker 的 query 文本通常用清洗后的原句 |

## Q3：任务书三条要求分别是什么意思？

任务书 `任务.txt` 共三块，对应 schedule 阶段 1–4。

### 3.1 任务一：多路检索（MultiPathRetriever）

**目标**：不只靠一种检索方式，而是**两路并行召回**，再合并，弥补单一方法的短板。

| 子任务 | 含义 | 为什么需要 |
|--------|------|-----------|
| **向量检索** | query → 嵌入向量 → Chroma 近似最近邻 Top-K | 擅长**语义相似**（同义改写、概念相关）；04 已建好库 |
| **BM25 关键词检索** | query 分词 → 在 chunk 全文上算 BM25 分 → Top-K | 擅长**精确词匹配**（药名、基因名、缩写展开后的词） |
| **构建 BM25 索引** | 读 03 chunks JSONL，建倒排 + 统计量 | BM25 不走 Chroma，需**单独索引**（语料 = chunk 的 `text`） |
| **融合策略** | 把两路排名合成一份列表 | 两路 Top-K 往往重叠又不完全相同，需要规则合并 |

**类比**：向量检索像「懂意思的图书管理员」；BM25 像「按关键词查卡片目录」；融合是「把两份推荐名单合成一张」。

### 3.2 任务二：重排序器（Reranker）

**目标**：融合后可能有几十条候选，**顺序还不够准**；用更强的模型对「query–文档对」逐条打分，把最相关的排到前面。

| 概念 | 含义 |
|------|------|
| **Bi-Encoder（04 BGE 嵌入）** | query、文档**分别**编码成向量，用距离比相似度；快，适合百万级召回 |
| **Cross-Encoder（bge-reranker-base）** | query 和文档**拼在一起**送进分类模型；慢，但更准；只适合对**少量候选**（如 30→10） |
| **多准则重排** | 不只看 relevance，还加权 **recency**（年份越新分越高）、**authority**（期刊权重） |

任务书示例权重：

```python
criteria_weights = {
    "relevance": 0.6,   # reranker 语义相关分
    "recency": 0.25,    # 时效性（来自 02 slim 的 pub_year）
    "authority": 0.15,   # 期刊权威性（规则表）
}
```

**注意**：年份/期刊不在 Chroma metadata 里（见 05 笔记 Q1），所以 **recency/authority 在检索之后、用 doc_id 回查** 再做特征分，而不是重建 04 索引。
回查采用 \06 检索系统开发第二部分\data\oa_comm_slim.jsonl （已从外部盘复制到本地）

### 3.3 任务三：完整检索流水线

**目标**：把 05 + 06 串成一条可演示、可评测的链路：

```text
query → enhancer → multipath retrieve → fuse → rerank → Top-K JSON
```

交付形态：`pipeline.py` + `notebooks/retrieval-pipeline.ipynb` + `scripts/run_retrieval_eval.py`。

## Q4：三种融合策略分别是什么？该默认用哪个？

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **simple** | 两路结果合并，按 `chunk_id` 去重 | 实现最简单 | **丢掉排名信息**——排第 1 和排第 20 一视同仁 |
| **rrf**（Reciprocal Rank Fusion） | 按名次算 `1/(k+rank)` 再相加（常用 k=60） | 不依赖两路分数尺度，**学术检索常用** | 需调 k；对极端分数不敏感 |
| **weighted** | 两路分数归一化后加权求和（向量权重大） | 可强调语义路 | 两路分数分布不同，归一化要小心 |

**本工程默认**：`rrf`（schedule 共识）；`weighted` 作备选对比。

## Q7：和 04「只有一种向量检索」相比，06 提升了什么？

| 维度 | 仅 04 向量 Top-K | 06 完整检索链 |
|------|-----------------|---------------|
| 召回 | 语义相近 | 语义 + 关键词，**漏召回更少** |
| 排序 | 向量距离一次定序 | 融合后再 **cross-encoder 精排** |
| 医学 query | 缩写/药名可能偏弱 | 05 扩展 + BM25 补精确匹配 |
| 时效/期刊 | 无 | recency / authority 可调权 |
| 时延 | 低（~十几 ms 量级 query） | 更高（BM25 建索引 + reranker 推理） |

**代价**：工程复杂度、内存（BM25）、推理时间（reranker）。典型做法：向量/BM25 各取 Top-20，融合后取 Top-30 再 rerank 到 Top-10。

## Q10：三种融合策略对比结果与默认策略取舍（样本库实测）

> 数据来源：`outputs/samples/fusion_examples.json`（C7 `strategy_compare`）+ `retrieval_compare.json`（C5 双路诊断）  
> 对比 query：`metformin cardiovascular effects`（向量路与 BM25 路 **Top-5 零重叠** 的典型 case）

### 10.1 三种策略 Top-5 实测（chunk_id）

| rank | simple | rrf（默认） | weighted |
|------|--------|-------------|----------|
| 1 | PMC523838_chunk2 | PMC523838_chunk2 | PMC523838_chunk2 |
| 2 | PMC524031 | **PMC521687** | PMC524031 |
| 3 | PMC524175 | PMC524031 | **PMC521687** |
| 4 | PMC524029 | **PMC521493** | **PMC521493** |
| 5 | PMC524503 | PMC524175 | PMC524175 |

**集合对比**：

| 对比 | Top-5 交集 | 说明 |
|------|-----------|------|
| simple vs rrf | 3/5 | rrf 替换 2 条纯向量结果，换入 BM25 独有候选 |
| rrf vs weighted | **4/5 相同集合**，仅 rank 2↔3 互换 | 两策略高度一致 |
| simple vs 向量路 | **5/5 完全相同** | simple 等价于「只信向量、后补 BM25 独有项」但本 case 无 BM25 补入 |

### 10.2 各策略含义与表现

| 策略 | 机制 | 本 case 表现 | 优点 | 缺点 |
|------|------|-------------|------|------|
| **simple** | 先向量列表，再追加 BM25 未出现项 | 与向量 Top-5 **完全一致** | 实现最简单 | **丢掉排名信息**；零重叠时 BM25 进不了 Top-5 |
| **rrf** | 按名次算 `1/(k+rank)` 求和（k=60） | 保留向量第 1，**第 2、4 位来自 BM25** | 不依赖分数尺度；双路都贡献；学术检索常用 |
| **weighted** | 分数 min-max 归一化后加权（向量 0.6） | Top-5 集合与 rrf **几乎相同** | 可调向量权重 | 归一化对 BM25 大分（~26）敏感；与 rrf 高度冗余 |

**字段怎么读**（C7 表格）：

- `vector_rank` / `bm25_rank`：该 chunk 在分路中的名次；`NaN` 表示未出现在该路 Top-K
- `fusion_score`：rrf/weighted 的最终融合分；simple 为 `NaN`（无融合分）

### 10.3 为什么选 **RRF** 作默认（而非 weighted 或 simple）

| 决策点 | 结论 |
|--------|------|
| **simple 是否可用** | ❌ 本 case 下等于放弃 BM25；C5 已证双路零重叠，simple **不满足**多路检索目标 |
| **rrf vs weighted** | 样本上 Top-5 **集合 80% 一致**；rrf 不依赖分数归一化，BM25（0~30+）与向量 cosine（0~1）尺度差异大时 **更稳** |
| **工程默认** | 维持 schedule 预设 **`fusion_strategy="rrf"`**；`weighted` 保留为可切换备选（调 `vector_weight` 做实验） |
| **是否删除其他策略** | ❌ 三种均保留在 `fusion.py` + C7 对比；默认只是 pipeline 入口的 config，不是淘汰赛 |

## Q12：C8 重排输出怎么读？（`rerank_examples.json`）

### 12.1 分数字段

| 字段 | 含义 |
|------|------|
| `relevance_score` | bge-reranker 对 query–doc 对的 sigmoid 概率（**语义相关**） |
| `recency_score` | 由 slim 回查 `pub_year` 线性映射；`year_gte` 时更早文献降权 |
| `authority_score` | 期刊规则表（Nature/Lancet/PLoS 等） |
| `final_score` | 加权合成：`0.6×rel + 0.25×rec + 0.15×auth` |
| `rerank_explain` | 上述分项 + `year_hint`（来自 05 filter 解析） |

### 12.2 实测要点

**`metformin cardiovascular effects`**

- 融合 RRF 第 1：`PMC523838_chunk2`（HIV lipid，向量路）
- 重排第 1：`PMC521687`（冠脉搭桥 stress，**BM25 路** keyword 命中）
- 说明：reranker 认为「心血管」相关，但**不含 metformin 字面**——样本库局限 + 融合已纳入 BM25 候选

**`papers on malaria after 2015`**

- `year_hint=2015` 已传入；但 Top 结果 `pub_year` 均为 **2004**（样本库无 2015+ 疟疾篇）
- `recency_score≈0.083`（2004 年相对 2015 阈值被惩罚），但因 `relevance_score` 也极低（~0.003），**未能把「更新」文献顶上来**
- 结论：recency 链路 **代码已通**；样本库 **语料时效** 不足以验证「after 2015」意图

## Q14：`pipeline_eval.json` 端到端结果怎么读？（阶段 5）

### 14.1 结构与指标

每条 query 包含：

| 块 | 含义 |
|----|------|
| `enhanced` | 05 增强结果（实体、keyword_query、filters） |
| `retrieval` | 向量路 / BM25 路 / `fused` 融合候选 |
| `reranked` | 最终 Top-K（含 relevance / recency / authority / final_score） |
| `latency_ms` | `enhance_ms` / `retrieve_ms` / `rerank_ms` / `total_ms` |

汇总 `summary`：

- `latency_ms.total_p50` / `total_p95`：批量时延
- `top1_chunk_ids`：各 query 最终顶位 chunk
