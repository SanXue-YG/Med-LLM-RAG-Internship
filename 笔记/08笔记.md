## Q1：第八阶段在整个 RAG 系统中做什么？处于什么位置？

### 一句话

**把 07 准备好的「上下文 + 四阶段 Prompt 剧本」真正交给本地 LLM（Ollama）执行，并串联 05→06→07 产出端到端医学 RAG 答案**——本周是整条在线链路的**最后一块拼图**：从用户提问到带引用、免责声明的最终 `answer`。

### 本周任务书两大块

| 任务书条目 | 通俗理解 | 规划产出 |
|-----------|---------|---------|
| **1. LLMGenerator** | 封装 Ollama：连得上、能生成、能解析 JSON（模型常带 markdown 围栏） | `llm_generator.py`、`json_utils.py` |
| **2. MedicalGenerationPipeline** | 把检索→组装→四步 Prompt→后处理串成一条 `run(query)` | `generation_pipeline.py`、`postprocess.py` |

### 端到端数据流（08 视角）

```text
用户 query（英文）
    ↓ 05 MedicalQueryEnhancer
    ↓ 06 RetrievalPipeline.run() → reranked
    ↓ 07 ContextAssembler.assemble() → context_text + selected_chunks
    ↓ 07 PROMPT_STAGES["evidence_evaluator"] → LLMGenerator（可选，JSON 输出）
    ↓ 按评估结果筛选 selected_chunks（doc_id / 标题行）
    ↓ PROMPT_STAGES["answer_generator"] → draft_answer
    ↓ PROMPT_STAGES["critical_reviewer"] → review_feedback（可选）
    ↓ PROMPT_STAGES["final_assembler"] 或草稿直出 → final_answer
    ↓ postprocess：引用 + 格式 + disclaimer
    → result（含 generation_metrics、intermediate_results、sources）
```

### 关键认知

1. **08 是「检索增强生成」里 G（Generation）的真正落地**——07 笔记 Q9 里「后续 LangChain / Ollama · 才调用 LLM」指的就是本周要完成的事；只是先用纯 Python 流水线实现，暂不引入 LangChain。
2. **一次用户提问 ≠ 一次 LLM 调用**——医学场景下默认最多 **4 次** LLM 调用（证据评估、起草、审查、终稿）；可选阶段可通过 `skip_evidence_eval` / `skip_critical_review` 关掉以加快调试。
3. **输入仍站在 06/07 肩膀上**——08 不重建索引、不重写组装逻辑；通过 `sys.path` 引用上游 `src`，与 05–07 开发方式一致。
4. **验证规模默认样本库**——与 06/07 一致用 `RetrievalPipeline.from_mode("sample")`；全量 `mode="full"` 留到 LangChain RAG 或上线前切换。
5. **本阶段边界清晰**——任务书要的是「能跑通的端到端生成流水线 + 指标 log」，不是聊天界面、不是流式输出、不是多模型路由。

### 任务书 `result` 结构在系统里的意义

| 字段 | 谁用 | 作用 |
|------|------|------|
| `answer` | 最终用户 / notebook 展示 | 后处理后的可读答案 |
| `sources` | 用户 + 审计 | 与答案内 `[1][2]` 对齐的文献列表 |
| `context_metadata` | 调试 | 07 组装统计（选了几个 chunk、估了多少 token） |
| `generation_metrics` | 评测 / 优化 | 各 stage 耗时、成功与否、token 估算 |
| `intermediate_results` | 调试 / 可选展示 | 证据评估 JSON、草稿、审查意见——07 里「内部中间步骤」本周有了实体 |
| `timestamp` | log | 可追溯每次生成时间 |

## Q2：当前 `schedule.md` 计划是否合理？（启动前审阅）

> 以下为 2026-06-29 对照任务书与 07 产出的审阅结论，供决定是否微调计划。

### 总体判断：**合理，可直接按 schedule 执行**

任务书三条（`LLMGenerator`、流水线整合、测试）与 schedule 阶段 0–6 一一对应；上游接口（06 `reranked`、07 `assemble` + `PROMPT_STAGES`）在 07 已验收，无结构性缺口。

### 与任务书对齐情况

| 任务书要求 | schedule 是否覆盖 | 备注 |
|-----------|------------------|------|
| Ollama 初始化 / 连接测试 | ✅ 阶段 0 + 1 `health_check` | 依赖 01 已验证的 `deepseek-r1:7b` |
| `generate` + system + temperature + max_tokens | ✅ 阶段 1 | `/api/generate` 或 `/api/chat` 二选一即可 |
| JSON 提取与修复 | ✅ 阶段 2 `json_utils` | evidence_evaluator 强依赖 |
| 批量生成 | ✅ 阶段 1 `generate_batch` | 首版顺序执行足够 |
| 六步流水线 + 可选 eval/review | ✅ 阶段 3 | 与任务书 Step 1–6 一致 |
| 引用 / 免责 / sources | ✅ 阶段 4 | 补全 07 笔记 Q9「chunk_id 默认不在 context 里」的缺口 |
| 测试 query + log 指标 | ✅ 阶段 5–6 | 4 条固定 query 表已写好 |

### 建议保留的设计决策（无需改计划）

| 决策 | 理由 |
|------|------|
| 先 **最小路径**（assemble → draft → postprocess，跳过 eval/review）再补全可选阶段 | 先证明 Ollama + 串联通，再叠 JSON 解析风险 |
| JSON 解析失败 → **不筛选**，用全部 `selected_chunks` | 避免误删有效证据导致答案变差 |
| mock 单测不依赖真实 Ollama | 与 07 的 pytest 策略一致，CI 可重复 |
| 样本库 `mode="sample"` | 与 06/07 notebook 一致，调试迭代快 |

### 可留意的风险（schedule 已写，执行时记住即可）

| 风险 | 对计划的影响 | 是否需改 schedule |
|------|-------------|------------------|
| `deepseek-r1` 输出冗长、带 `` 围栏 | JSON 阶段易失败 | ❌ 已有 `extract_json` + skip 降级 |
| 四步 LLM 端到端耗时长 | notebook 调试慢 | ❌ 开发期可 `skip_critical_review=True` |
| 07 四阶段模板尚未把①②③输出喂给下一步 | 08 需在 pipeline 里**显式串联**中间产物 | ⚠️ 见下「可选微调」 |
| 01 Ollama 未启动 | C0 即失败 | ❌ 阶段 0 健康检查已规划 |
