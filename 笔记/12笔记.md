## Q1：第十二阶段在整个 RAG 系统中做什么？处于什么位置？

### 先用大白话说清楚

11 已经把「后厨」（01–10）封成了 **HTTP 点餐口**：外部可以用 `POST /api/v1/qa` 问一句、拿答案，不必再开 Jupyter、也不必 import 各阶段源码。

但 11 交付的仍是 **最小可用接入层**：

| 11 已有 | 11 刻意没做满 / 很薄 |
|---------|----------------------|
| 统一信封、错误码、`/health`·`/ready` | 产品级运维面板 |
| 同步/伪流式问答 | 完整会话 CRUD |
| 内存会话 + 可选 `GET sessions/{id}` | 显式创建/删除会话、多轮运营口径 |
| `qa_calls.jsonl` 落盘 | **运营统计 API**（次数/耗时/成功率） |
| 探活探针 | **组件健康汇总**（LLM / 向量库 /「数据库」） |
| — | **文档列表 / 按 id 查询** |
| `/docs` 能开 | Postman、`.env`、部署与调用说明成套交付 |

本周（12）做的是：在 **同一条服务化主线**上，把「柜台」从「能点餐」补成「能管桌、能看流水、能查菜单（文献元数据）、能按文档验收」——仍是 **API / 运维面**，**不是**再写检索、生成或约束算法。

对照记忆：

| 阶段段 | 在干什么 | 入口形态 |
|--------|----------|----------|
| 01–04 | 离线：数据与向量库 | 脚本 / notebook |
| 05–08 | 在线：检索 + 生成「答得出」 | Python `pipeline.run` |
| 09 | 外侧：打分 / 缓存 / 批量 | CLI + notebook |
| 10 | 横切：硬纪律 + 交卷安检 | Python 约束流水线 |
| **11** | **服务化上半：骨架 + 问答接口** | FastAPI（`/qa` · 伪 SSE） |
| **12（本周）** | **服务化下半：会话 / 运营统计 / 文档管理 + 测试与部署配套** | **同一 FastAPI 上的管理与观测 API** |

一句话：

> **11 解决「别人怎么用 HTTP 问一句」；12 解决「会话怎么管、运营数据怎么看、文献元数据怎么查、以及这套 API 怎么测、怎么配、怎么部署说明」。**  
> 本周仍是 RAG 的 **服务接入层 / 运维与资源面扩展**，**不重做** 05–10 内核。

### 餐厅比喻（把 11 / 12 放在同一画面里）

```text
01–10 = 后厨（建库 → 检索 → 组装 → 生成 → 评估/缓存 → 强约束）

11    = 前台点餐系统（刚开张）
      · 统一小票（ResponseModel）
      · 点餐口：同步 / 伪流式问答
      · 桌号 session_id（最小关联）+ 流水账 qa_*.jsonl
      · 探活：店开着吗（/health · /ready）

12    = 前台「管理与运营」补齐（同一家店，不换后厨）
      · 开桌 / 查桌历史 / 撤桌（会话 CRUD；点餐时自动记账）
      · 经理看报表：几单、多快、成不成功（stats/qa）
      · 库存与灶台状态：文献量、索引体积、增量次数占位；LLM/向量库健康（stats/index · stats/health）
      · 菜单册查询：按列表 / 按菜名 id 查文献元数据（documents，只读）
      · 验收配套：单测 + Postman、Swagger 写清楚、.env、部署与调用示例
```

要点：**12 不换菜谱、不改建库、不重写 10 安检**——在 11 的柜台协议上，补「桌台管理 + 经营数据 + 菜单查询 + 交付文档」。

### 端到端数据流（12 视角）

```text
Client
  ├─ POST /api/v1/sessions
  │     → SessionStore.create → session_id
  │
  ├─ POST /api/v1/qa (+ session_id)
  │     →（11）RagService → 10/08 流水线
  │     → SessionStore.append(user / assistant)   ← 任务书「添加消息由问答自动调用」
  │     → qa_logger JSONL
  │
  ├─ GET  /api/v1/sessions/{id}     → 历史消息列表
  ├─ DELETE /api/v1/sessions/{id}   → 删除会话
  │
  ├─ GET  /api/v1/stats/qa          → 聚合 JSONL（次数 / 耗时 / 成功率）
  ├─ GET  /api/v1/stats/index       → Chroma count / 目录大小 / 增量占位…
  ├─ GET  /api/v1/stats/health      → LLM · 向量库 · database(skipped?) · API
  │
  └─ GET  /api/v1/documents[/{id}]  → DocumentStore（slim 子集 / 样本索引）
        未命中 → 3001
```

### 关键认知

1. **12 仍是服务化，不是「又一个算法周」**——质量与安全仍靠 08/09/10；本周交付的是管理面、观测面与文档查询面。
2. **问答主路径继续走 11 `RagService` → 10**——会话/统计/文档是**旁路能力**，不要为了 stats 去改生成内核。
3. **会话：从「关联」升级到「可管理」**——任务书要的是显式 API；多轮上下文注入可延续 11 的 query 前缀 MVP，不必假装上游已有原生 `session_history`。
4. **统计：把已有日志/探针「接口化」**——优先读 `qa_calls.jsonl` 与 Chroma 元信息；「增量更新次数」「数据库健康」若无数据源，应用占位/`skipped` 写进文档，避免假实现。
5. **文档管理 = 只读元数据查询**——不是 02/04 的入库流水线，也不是增量写 API；全量 slim 太大 → MVP 用样本索引 / 预建轻量表。
6. **测试与文档是任务书第三块，不是「有空再写」**——Postman、`.env`、部署说明与 sessions/stats/documents 同级交付。
7. **本阶段边界**：不做前端 UI、不做真实鉴权落地、不做生产 K8s、不做增量入库写接口——与 schedule「启动前决策」一致。

## Q5：阶段 5 已经尽量用全量了，为什么还会碰到「样本」？

> 一句话先答：**阶段 5 的全量，主要是「问答检索用的大库」；文献列表 `/documents` 我们本周只准备了一本小名册，所以列表还是样本。两件事不是同一个开关。**

### 系统里其实有两套东西

| | 干什么 | 阶段 5 用什么 |
|--|--------|----------------|
| **检索库**（Chroma / BM25） | `/qa` 找文献、生成答案 | **全量**（约 610 万块） |
| **文献名册**（`documents_sample.json`） | `/documents` 翻列表、按 id 查标题摘要 | **样本小名册**（本周 MVP） |

阶段 5 要还原的「正式使用」，核心是：**用户提问 → 全库检索 → 出答案**。  
这件事靠检索库，已经按全量跑。

`/documents` 是另一件事：**像目录一样浏览/点开一篇文献的元数据**。  
本周任务只要求「有列表和按 id 查询的接口」，没有要求「能翻完整个 PMC 库」，所以名册只做了样本版。

### 为什么名册不顺手改成全量？

全库有大约 **四百多万篇** 文献元数据（slim 文件很大）。  
若阶段 5 临时拿全量当列表用，就要么：

- 每次启动读进内存 / 扫盘 → **极慢、不现实**；要么  
- 另外再做一套「全库文档索引」→ **等于多做一个子系统**，超出本周范围。

所以：**不是阶段 5「做不到全量问答」，而是「全量文献目录」还没做、本周也不打算做。**

### 你会具体看到什么「样本残留」

- `/qa`：全量，正常。  
- `/stats` 里表示「块有多少」：全量数字。  
- `/documents` 列表：仍是小名册。  
- 用全量 `/qa` 返回的某个 pmcid 去 `/documents/{id}`：小名册里没有 → 可能 **3001**（文献其实在全库里，只是没进名册）。

这不代表全量仿真失败，只说明：**问答走全库，目录走小册。**

### 若以后要「正式使用也一点样本味都没有」

需要单独做「全库文献名册/索引」，再让 `/documents` 读它——工期估算见 **Q7**。

## Q7：若要建「全库文档索引」，大概要多久？

> 日期：2026-07-27。对应 Q5：把 `/documents` 从样本小名册升级到能服务全库（~455 万篇，数据源 `Dataset/processed/oa_comm_slim.jsonl` ≈ 8.9 GB）。

### 要做成什么样（先定范围）

| 档位 | 能力 | 用途 |
|------|------|------|
| **A. 最小** | 按 `pmcid` 秒级查询；能 `COUNT(*)` | 阶段 5 里全量 `/qa` 返回的 id 不再轻易 3001 |
| **B. 任务书对齐** | A + **分页列表**（可先不做标题模糊搜） | `/documents` 与 `/documents/{id}` 都走全库 |
| **C. 好用** | B + 标题关键词（如 SQLite FTS）+ 列表不塞全文 abstract | 接近「正式文献目录」 |

推荐落地形态：**一次离线从 slim 流式写入 SQLite**（`pmcid` 主键），API 只读库；**不要**每次请求扫 8.9 GB JSONL，也**不要**把 455 万行 JSON 一次载入内存。

### 机器跑数（墙钟，粗估）

本机 SSD、单进程流式读 slim + 批量写入 SQLite，经验量级：

| 步骤 | 粗估 |
|------|------|
| 扫完 slim 建库（455 万行） | **约 0.5–2 小时**（磁盘/是否写 abstract 影响大） |
| 建主键后按 id 查询 | 毫秒级 |
| 深分页 `OFFSET` 很大 | 会变慢 → 列表应用「翻页游标」或限制最大页 |

→ **纯跑数据**：多留 **半天内** 一次即可；可过夜跑。不是按「天」计的瓶颈。

### 人开发要多久（按你现在这套 FastAPI / 单人）

| 档位 | 编码 + 联调 | 说明 |
|------|-------------|------|
| **A 最小** | **约 0.5–1 天** | 建库脚本 + DocumentStore 改读 SQLite + 单测；阶段 5 验证 qa→get |
| **B 任务书对齐** | **约 1.5–2.5 天** | A + 分页列表（注意别用大 OFFSET）+ `document_count` 改全库篇数 + 文档/README 重建说明 |
| **C 好用** | **再加约 1–1.5 天** | 标题 FTS、列表字段裁剪、构建进度/校验 |

合计常见口径：

- **只为阶段 5「去样本味」（A）**：**1 天左右**（含一次建库等待）。
