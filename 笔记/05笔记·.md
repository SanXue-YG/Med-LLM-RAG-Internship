## Q1：「Chroma metadata」是什么？它等于 `chunks_sample.jsonl` 吗？

### 一句话

**不等于。** `chunks_sample.jsonl` 是建库**之前**的输入文件；**Chroma metadata** 是建库**之后**写在 `chroma.sqlite3` 里、每条向量附带的一小份「标签字段」，供检索结果展示和 `where_filter` 过滤。

### 三者关系（输入 → 入库 → 检索）

```text
chunks_sample.jsonl / oa_comm_chunks.jsonl     ← 【输入数据集】一行 = 一个 chunk
        │
        │  index_builder.build_from_jsonl()
        │  collection.add(ids, embeddings, documents, metadatas)
        ▼
chroma_db_full/chroma.sqlite3                  ← 【Chroma 主库】
        ├── embeddings   （384 维向量）
        ├── documents    （chunk 全文 text，与 JSONL 重复存一份）
        └── metadatas    ← 【这就是「Chroma metadata」】
        │
        └── <uuid>/      （HNSW 目录，只加速检索，不存业务 metadata）

用户 query → query() → 返回 ids + documents + metadatas
```

### 本工程实际写入的 Chroma metadata 字段

来源：`04 .../src/index_builder.py` 的 `METADATA_FIELDS`，从 JSONL **按字段名拷贝**（JSONL 里没有的就不会进 metadata）：

| 字段 | JSONL 有？ | Chroma metadata 有？ |
|------|-----------|---------------------|
| `chunk_id` | ✅ | 作为 `ids`，不在 metadatas 里 |
| `text` | ✅ | 作为 `documents`，不在 metadatas 里 |
| `doc_id` | ✅ | ✅ |
| `chunk_index` | ✅ | ✅ |
| `total_chunks` | ✅ | ✅ |
| `source_title` | ✅ | ✅ |
| `token_count` | ✅ | ✅ |
| `strategy` | ✅ | ✅ |
| **`pub_year` / `pub_date` / `journal`** | ❌（chunk JSONL 未带） | ❌ |

### 和 `chunks_sample.jsonl` 的对比

| | `chunks_sample.jsonl` | Chroma metadata |
|--|----------------------|-----------------|
| **是什么** | 磁盘上的 JSONL 文件（1267 行样本） | sqlite 里每条向量绑定的键值对 |
| **是否等于向量库** | 否，只是**原料** | 是向量库**的一部分** |
| **正文在哪** | `text` 字段 | `documents` 表 + JSONL 各一份 |
| **能否被 Git 跟踪** | 样本文件可 git；全量 JSONL 通常不 git | 在 `chroma_db_full/`，`.gitignore` 排除 |

### 为何 04 笔记里说「metadata 没有 pub_year」？

因为 **03 阶段输出的 chunk JSONL 就没有日期字段**（03 任务书只要求 doc_id、chunk_index、source_title 等），04 建库时 **`METADATA_FIELDS` 只拷贝 chunk 里已有的键**，没有把 02 阶段 slim JSONL 里的 `pub_year` / `journal` 并进来。

02 正式报告（`RAG数据分析与设计说明.md` §7）里写过：`pub_year` 覆盖率 ~99%，**未来**可用于「近 5 年」过滤——那是**数据评估阶段的规划**，不是 03/04 任务书的硬性交付。

## Q2：日期过滤在各阶段怎么出现的？05 阶段「提取过滤条件」是必选还是可选？现在还能用哪些 filter？对 RAG 有何影响？如何补救？

### 2.1 各阶段对「日期 / 期刊」的需求时间线

| 阶段 | 任务书是否要求把日期写入 chunk / Chroma | 实际做了什么 |
|------|----------------------------------------|--------------|
| **02 数据处理** | **分析** journal、pub_date；判断**未来**能否做「近 5 年《Nature》」过滤 | slim JSONL **含** `pub_year`、`pub_date`、`journal`；写入正式报告 §7 |
| **03 文档分割** | 只要求 chunk 元数据：doc_id、chunk_index、source_title 等 | **未**把 pub_year 带进 `oa_comm_chunks.jsonl` |
| **04 向量化建库** | 任务书 stats / metadata_fields，**未列** pub_year | 只入库 6 个 chunk 字段（见 Q1 表） |
| **05 检索（本周）** | 「从查询中**提取**过滤条件（**时间范围等**）」 | **解析查询**产出 `filters` 结构；**未要求**本周就必须在 Chroma 上生效 |

结论：**日期是 02 起的长期能力规划 + 05 查询解析的举例（「等」= 不限于时间），不是 03/04 漏做的硬性任务。**

### 2.2 本阶段「提取过滤条件」：必选 vs 可选

| 层次 | 是否本周必须 | 说明 |
|------|-------------|------|
| **实现 `extract_filters()` 一类逻辑** | ✅ **建议做** | 任务书流程明确列出「提取过滤条件」 |
| **时间范围这一种 filter** | ⚠️ **举例，非唯一必做项** | 原文是「时间范围**等**」——strategy、doc 类型等都可解析 |
| **解析出的 filter 立刻作用于 Chroma** | ❌ **非本周必须** | 任务书本周产出是「查询理解与增强**代码**」，不是完整检索管线 |
| **filter 在 Chroma 上 100% 生效** | ❌ **当前做不到年份** | 因 metadata 无 `pub_year`（见 Q1） |

**共识（与 schedule 一致）：**

- 05 阶段：**必须**能从自然语言里**解析**出结构化 `filters`（如 `year_gte: 2015`、`strategy: sliding_window`）。
- **可以**在 `EnhancedQuery.metadata` 里标注 `year_filter_index_supported: false`，避免误以为已能筛「近 5 年」。
- **不必**为交差而假装 Chroma 已支持年份过滤。

### 2.3 当前数据集**已经可用**的过滤条件

这些字段**已在 Chroma metadata**，04 C5 已验证（`strategy=sliding_window`，大库走 post-filter）：

| filter 示例 | 字段 | 能否用于 Chroma / RAG |
|-------------|------|------------------------|
| 只要滑动窗口切分的块 | `strategy == "sliding_window"` | ✅ 已验证 |
| 只要单块文献 | `strategy == "single"` | ✅ |
| 指定 PMC 号 | `doc_id == "PMC176545"` | ✅ 等值过滤 |
| 某文献的第 i 块 | `chunk_index` + `doc_id` | ✅ |
| 标题关键词（若实现层支持） | `source_title` | ⚠️ Chroma `where` 能力有限，常需检索后过滤 |

**当前不可用（需补救才可以在索引层过滤）：**

| filter 示例 | 缺什么 |
|-------------|--------|
| 2015 年以后 | metadata 无 `pub_year` / `pub_date` |
| 《Nature》期刊 | metadata 无 `journal`；02 报告也指出 journal **未标准化** |

### 2.4 对 RAG 系统的影响

| 场景 | 影响 |
|------|------|
| **普通语义问答**（不强调年份/期刊） | **几乎无影响**——BGE + Chroma 语义 Top-K + LLM 即可 |
| **「近 5 年二甲双胍研究」** | **有影响**——若不在检索链加年份约束，可能召回很老的 PMC 摘要 |
| **合规 / 时效性强的临床场景** | **有影响**——需要在检索后或检索前加年份约束 |

RAG 仍可做，只是「按时间/期刊精筛」要额外一层，不能单靠现有 Chroma metadata。

### 2.5 补救方法（按推荐顺序）

#### 方案 A：建库时把 02 字段并入 metadata（**索引层过滤，长期最佳**）

1. 从 `oa_comm_slim.jsonl` 按 `pmcid == doc_id` 建 lookup 表（`pub_year`, `journal` 等）。
2. 修改 04 `build_from_jsonl` / `METADATA_FIELDS`，入库时写入这些字段。
3. **全库重新 embedding 或** 若 Chroma 支持仅 update metadata（610 万条 update 也需评估耗时）→ 更稳妥是 **保留向量、批量 update metadatas**（若版本支持）或 **重建索引**。
4. 05 的 `filters.year_gte` 即可映射为 Chroma `where`（大库仍可能需要 post-filter）。

#### 方案 B：**检索后过滤**（**不改索引，开发快**）

1. 语义检索先取 Top-K'（K' > 最终 K，如 50）。
2. 用 `doc_id` 查 slim JSONL / 本地 pmcid 索引表，读 `pub_year`，丢弃不符合的。
3. 05 本周即可设计接口：`filters` 解析结果传给「后过滤模块」（下一阶段实现）。

#### 方案 C：**两阶段检索**（先筛 doc_id 再向量搜）

1. 对 slim JSONL 预建「pub_year ≥ 2019 的 pmcid 集合」。
2. 查询时限定 `doc_id in {...}`（数据量大时要分桶或倒排，工程复杂度较高）。

**建议路径：** 05 只做 **filter 解析 + 文档说明**；RAG 联调阶段用 **方案 B** 快速验证；若老师强调「近 5 年」产品化，再投入 **方案 A** 补 metadata。

完整 HNSW 落盘时，应对应 uuid 目录下的 **`data_level0.bin` 等 bin 文件**（见 04 笔记 Q18），不是 `.bak`。

### 5.2 RAG 会不会用到 HNSW？怎么用？

**会，但是间接使用——你不写 HNSW 代码，Chroma 在内部用。**

```text
RAG 检索链（后续阶段）
  用户 query → 05 增强 → DocumentEmbedder.encode_queries() → 384 维向量
       → ChromaIndexBuilder.query() / collection.query()
       → 【Chroma 内部用 HNSW 做近似最近邻】→ Top-K chunk
       → 拼进 Prompt → LLM
```

| 角色 | 说明 |
|------|------|
| **你写的代码** | 只调 `query()`，传 query 向量 |
| **HNSW** | Chroma 的加速结构，在 `query()` 内部选 Top-K |
| **sqlite** | 存向量与正文；HNSW 缺失或损坏时，Chroma 可能改走 sqlite/内存路径（本机实测 `query()` 仍可用） |

**对日后 RAG 的影响：**

| 情况 | 影响 |
|------|------|
| sqlite 完整 + `query()` 正常 | ✅ **无实质影响**，照常开发 05 检索与 RAG |
| 报 `Error loading hnsw index` | ⚠️ 需修复/触发重建，**不是**重跑 embedding |
| 无 bin 但 query 可用 | ✅ 可继续用；若担心性能，可主动触发重建让 bin 落盘 |

### 5.3 若打算从 sqlite 重建 HNSW，如何操作？

**原则：只重建检索目录，不重新算 BGE 向量。**

**步骤（推荐顺序）：**

1. **确认主数据在**  
   ```python
   from index_builder import count_embeddings_sqlite
   count_embeddings_sqlite(r"D:\谷歌\04 向量化与索引构建\data\chroma_db_full")
   # 应为 6107296
   ```

2. **清理损坏的 HNSW 段**（不动 `chroma.sqlite3`）  
   - 方式 A：notebook / 脚本调用 `repair_chroma_hnsw(persist_dir, "pmc_oa_comm_full")`  
   - 方式 B：手动删除 uuid 目录内 **`index_metadata.pickle`**（`.bak` 可删可留）；若整目录损坏可 `rmtree` 该 uuid 目录（**勿删** `chroma.sqlite3`）

3. **重新 attach 并触发 compaction**  
   ```python
   import sys
   sys.path.insert(0, r"D:\谷歌\04 向量化与索引构建\src")
   from embedder import DocumentEmbedder
   from index_builder import ChromaIndexBuilder

   PERSIST = r"D:\谷歌\04 向量化与索引构建\data\chroma_db_full"
   emb = DocumentEmbedder()
   builder = ChromaIndexBuilder(PERSIST, "pmc_oa_comm_full", emb)
   r = builder.query("malaria vaccine", n_results=5)  # 触发内部索引加载/重建
   ```

4. **检查 uuid 目录**  
   若重建成功落盘，应出现 `data_level0.bin`、`link_lists.bin` 等（体积会很大）。  
   **未出现 bin 但 `query()` 正常**：Chroma 1.5.x 可能仅用内存/sqlite 路径，**仍可用于 RAG**，不必因此重跑 C2.5b。

5. **最后手段（极耗时）**  
   仅当 `chroma.sqlite3` 损坏或条数不对：从 E: 备份整目录拷回，或 `vectorize-index-full.ipynb` **RESUME=True** 重跑建库（会重新 embedding，**不是** HNSW 重建）。

> **不要混淆**：HNSW 重建 ≠ 全量 re-embed。前者数分钟级（视 Chroma 行为而定），后者数小时级。

## Q6：05 阶段在 RAG 中的位置（补充共识）

| `filters` | 解析用户意图（含年份、期刊）；**能执行的**走 Chroma，**不能的**标注后留给检索后过滤或补 metadata |

## Q10：全量库无 HNSW bin，RAG 会占更多内存、有爆内存风险吗？

### 10.1 简短结论

**一般不会因「磁盘上没有 bin」就在每次 query 时把 610 万向量全载入 RAM。**  
但 **首次 attach / 首次 query** 时 Chroma 可能做 compaction、在内存或 mmap 中重建 HNSW，**可能出现一次性内存/时间尖峰**。日常 RAG 的 Top-K 检索（K=5~20）与有 bin 时同属近似最近邻，**不是**全表扫描。

### 10.2 内存主要花在哪（RAG 阶段）

| 组件 | 粗算 | 说明 |
|------|------|------|
| **BGE-small** | ~0.5–1.5 GB（GPU 显存为主） | 与有无 bin **无关** |
| **本地 LLM（如 7B）** | **数 GB～10+ GB** | RAG 主要内存压力，通常 **大于** Chroma |
| **Chroma / HNSW** | 向量 ~9 GB 量级（常 **mmap** sqlite，非整库进 RAM） | bin 在盘上时也多通过 **mmap** 访问，不等于「不占内存」 |
| **单次 query** | 很小 | 只取 Top-K 条 metadata + documents |

### 10.3 无 bin vs 有 bin

| | 有 `data_level0.bin` | 无 bin（当前全量库常见态） |
|--|---------------------|---------------------------|
| 查询路径 | mmap / 加载 HNSW 图 | 可能先 compaction 再建图，或走 sqlite 恢复 |
| 稳态 query 内存 | ANN 图 + mmap | 恢复后 **类似** |
| 风险点 | bin 损坏 → 加载失败 | **首次**打开/查询可能更慢、内存短暂升高 |

### 10.4 实务建议（12GB 显存笔记本）

1. **RAG 进程内只保留一个 `PersistentClient`**，勿重复打开多个全量库。  
2. **先做一次** `repair_chroma_hnsw` + smoke `query()`，让库进入稳定态（可选观察是否写出 bin）。  
3. **LLM 与 BGE 分时加载**或量化模型，比纠结 Chroma bin 更重要。  
4. 若长期无 bin 且 query 变慢/内存持续涨，再考虑从 E: 备份 attach 或触发重建 HNSW（仍 **不需** re-embed）。

**对 05 smoke test**：样本库 1267 条 **无爆内存顾虑**；全量仅试少量 query 同样安全。
